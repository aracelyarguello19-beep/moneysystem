## Story

**As a** dueño de cuenta,
**I want** poder ver los indicadores del negocio activo filtrados por período y separados entre productos y servicios,
**so that** pueda entender qué parte de ese negocio rinde más.

## Acceptance Criteria

1. El usuario puede filtrar el dashboard de indicadores del negocio activo por un rango de fechas (FR22).
2. El usuario puede ver el desglose de CMV/CSV y de Ganancia Bruta de ese negocio, separado entre ítems tipo producto e ítems tipo servicio.
3. Cambiar el período o el desglose no requiere recargar toda la aplicación ni esperar más de unos segundos.

## Dev Notes

### Previous Story Insights

Depende directamente de Story 5.1 (`calcularIndicadores`, ya calcula CMV separado de CSV internamente por tipo de ítem) — esta story expone ese desglose ya calculado en la UI y agrega el filtro de período como parámetro de entrada, no un cálculo nuevo desde cero.

### Cálculo de referencia (de Story 5.1) que esta story desglosa

- CMV: suma de `Item.costoCompra * cantidad` vendida de ítems tipo Producto.
- CSV: suma de `VentaItem.costoServicio` (tratado como 0 si `null`) de ítems tipo Servicio.
- Ganancia Bruta = Ingresos Netos − CMV − CSV.
El desglose de esta story consiste en calcular Ganancia Bruta parcial atribuible a cada grupo (producto vs. servicio) manteniendo la misma fórmula base, no una fórmula alternativa.
[Source: architecture/data-models.md#Item, architecture/data-models.md#Venta / VentaItem]

### Server Action de referencia (a extender)

```typescript
// actions/indicadores/obtener-indicadores.ts
export async function obtenerIndicadores(
  negocioId: string,
  periodo: PeriodoFiltro
): Promise<Result<IndicadoresFinancieros, ApiError>>;
```
El parámetro `periodo: PeriodoFiltro` ya está en la firma representativa del contrato de API — esta story es la que define e implementa efectivamente ese tipo y su efecto sobre la consulta.
[Source: architecture/api-specification.md#Convención de Server Actions]

### State Management — filtro sin reload (AC 3)

React Query con `staleTime` corto (30s); cambiar `periodo` cambia la `queryKey`, lo que dispara un refetch scoped sin recargar el resto de la aplicación — mismo patrón que Story 5.1 usa para el recálculo en tiempo real.
[Source: architecture/frontend-architecture.md#Frontend Services Layer]

### Completion Notes List

- **Solapamiento intencional con Story 5.1, documentado.** `PeriodoFiltro` y el filtro de fechas en la UI ya se habían implementado en Story 5.1 porque `obtenerIndicadores` los necesitaba en su propia firma desde el principio — esta story los reutiliza en vez de "definirlos" de nuevo como sugieren sus Dev Notes (que fueron escritos antes de que 5.1 se implementara en esta misma sesión).
- **Task 1 — completa.** El desafío real era matemático, no de UI: para que `desglose.producto.gananciaBruta + desglose.servicio.gananciaBruta` sea exactamente igual a `gananciaBruta` global (Task 4, "sin doble conteo ni omisión"), había que decidir qué hacer con `venta.impuesto`, que es un campo por venta, no por línea. Se resolvió prorrateando el impuesto de cada venta entre sus líneas según la participación de cada línea en el bruto de esa venta — así cada término de la suma global queda particionado exactamente entre Producto y Servicio, garantizado por construcción (se calcula todo en el mismo recorrido de datos que produce los totales, no en una pasada separada que podría desincronizarse).
- **Task 2/Task 3 — completas, reutilizando la UI de Story 5.1** en vez de crear un directorio `components/dashboard/` nuevo — el panel de indicadores de esa story ya era el lugar natural para mostrar el desglose, no había necesidad de una vista separada.
- **Task 4 — completa.** El test de "no doble conteo ni omisión" usa una venta con impuesto y dos ítems (Producto + Servicio) para forzar el caso de prorrateo, más un caso "solo servicio" para confirmar que el lado de Producto queda en cero sin ensuciarse. El test de componente verifica el efecto observable de "no recargar todo" (el panel sigue montado, mismo contenido en el DOM) tras cambiar el período — no se puede testear literalmente "no hay reload de página completa" en jsdom sin mockear el router de Next.js, así que se verificó el proxy más directo: la Server Action se vuelve a llamar con el nuevo período sin que el componente se desmonte.
- Story queda en `Ready for Review`. Sin salvedades funcionales — la única nota es la ausencia de React Query (ya documentada en Story 5.1/2.3/4.3, no es un problema nuevo de esta story).
