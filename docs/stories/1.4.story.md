## Story

**As a** dueño de cuenta,
**I want** dar de alta uno o varios negocios dentro de mi cuenta y cambiar entre ellos,
**so that** pueda operar cada uno como una unidad independiente.

## Acceptance Criteria

1. El usuario puede crear un negocio nuevo dentro de su cuenta indicando al menos un nombre (FR3).
2. El usuario puede crear más de un negocio en la misma cuenta; cada uno queda registrado con un identificador interno independiente.
3. El usuario puede ver y usar un selector de negocio activo disponible en cualquier pantalla del módulo Laboral, y cambiar el negocio activo en cualquier momento (FR5).
4. El usuario puede archivar o dar de baja un negocio; un negocio archivado no acepta nuevas transacciones, pero su historial permanece consultable (FR4).
5. Dar de alta un negocio nuevo se completa en menos de 2 minutos (NFR11).

## Dev Notes

### Previous Story Insights

Story 1.3 estableció `withRlsContext` como única vía de acceso a datos por cuenta; esta story es la primera en usar `negocioId` como segundo parámetro de contexto RLS (Story 1.5 refuerza el aislamiento entre negocios).

### Data Model — Negocio

```typescript
export interface Negocio {
  id: string;
  cuentaId: string;
  nombre: string;
  estado: "ACTIVO" | "ARCHIVADO";
  createdAt: Date;
  archivedAt: Date | null;
}
```
Entidad intermedia obligatoria: toda tabla transaccional o de catálogo del módulo Laboral referencia un `negocioId`. Una `Cuenta` tiene muchos `Negocio` (FR3).
[Source: architecture/data-models.md#Negocio]

### Database Schema — tabla `negocios`

```sql
create table negocios (
  id           uuid primary key default gen_random_uuid(),
  cuenta_id    uuid not null references cuentas(id) on delete cascade,
  nombre       text not null,
  estado       text not null default 'ACTIVO' check (estado in ('ACTIVO','ARCHIVADO')),
  created_at   timestamptz not null default now(),
  archived_at  timestamptz
);
create index idx_negocios_cuenta on negocios(cuenta_id);
alter table negocios enable row level security;
create policy negocios_isolation on negocios using (cuenta_id = auth.uid());
```
[Source: architecture/database-schema.md]

### API Specification — `crearNegocio`

```typescript
// actions/negocios/crear-negocio.ts
export async function crearNegocio(
  input: CrearNegocioInput
): Promise<Result<Negocio, ApiError>>;
```
Toda Server Action valida su input con Zod (`packages/domain`), resuelve la cuenta autenticada desde la sesión, ejecuta la operación dentro de `withRlsContext`, y devuelve `Result<T, ApiError>` — nunca lanza excepciones no controladas hacia el cliente.
[Source: architecture/api-specification.md#Convención de Server Actions]

### State Management — Negocio Activo

```typescript
// stores/negocio-activo.store.ts
interface NegocioActivoState {
  ambito: "LABORAL" | "PERSONAL";
  negocioActivoId: string | null;   // null solo si ámbito === "PERSONAL" o no hay negocios aún
  setAmbito: (ambito: "LABORAL" | "PERSONAL") => void;
  setNegocioActivo: (negocioId: string) => void;
}
```
Persistido en `localStorage` (zustand/middleware persist) — recuerda la última selección entre sesiones, sin volver a pedirla. Zustand se usa solo para estado de UI efímera/navegación (negocio activo, ámbito) — nunca para datos que vienen del servidor (esos van con React Query).
[Source: architecture/frontend-architecture.md#State Management Architecture]

### Coding Standards Relevantes

- Server Actions como Única Puerta de Mutación: ningún Client Component hace `fetch` a un endpoint propio para mutar datos de dominio — siempre invoca una Server Action importada.
- Revalidation Explícita: toda Server Action que muta datos llama a `revalidatePath`/`revalidateTag` sobre las rutas que dependen de esos datos antes de retornar.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]
