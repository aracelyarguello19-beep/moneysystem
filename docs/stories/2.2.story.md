## Story

**As a** dueño de cuenta,
**I want** registrar, en el negocio activo, cada compra de mercadería con su costo,
**so that** el stock y el costo del producto de ese negocio queden actualizados automáticamente.

## Acceptance Criteria

1. El usuario puede registrar una compra dentro del negocio activo, indicando producto, costo unitario, cantidad, fecha, proveedor opcional y forma de pago (efectivo/banco/tarjeta de crédito/a crédito con proveedor) (FR12).
2. La compra solo admite ítems tipo Producto del catálogo del negocio activo; un ítem tipo Servicio no aparece como opción.
3. Al confirmar la compra, el stock del producto aumenta en la cantidad comprada y el saldo de la cuenta/medio de pago usado, dentro de ese negocio, se actualiza según corresponda.
4. Si la forma de pago es tarjeta de crédito, la deuda de tarjeta de ese negocio aumenta en el monto de la compra (ver Epic 4).

### Data Model — Compra

```typescript
export type FormaPagoCompra = "EFECTIVO" | "BANCO" | "TARJETA" | "CREDITO_PROVEEDOR";

export interface Compra {
  id: string;
  negocioId: string;
  itemId: string;
  costoUnitario: string;
  cantidad: string;
  fecha: Date;
  proveedor: string | null;
  formaPago: FormaPagoCompra;
  cuentaFinancieraId: string | null;  // null solo si CREDITO_PROVEEDOR
  monedaId: string;
  tasaCambioId: string | null;        // null si moneda == base
}
```
Relationships: Pertenece a `Negocio` e `Item`; afecta `CuentaFinanciera` (saldo) o genera deuda de tarjeta (`MovimientoTarjeta`).
[Source: architecture/data-models.md#Compra]

### Database Schema — tabla `compras`

```sql
create table compras (
  id                  uuid primary key default gen_random_uuid(),
  negocio_id          uuid not null references negocios(id) on delete cascade,
  cuenta_id           uuid not null references cuentas(id) on delete cascade,
  item_id             uuid not null references items(id),
  costo_unitario      numeric(18,4) not null check (costo_unitario >= 0),
  cantidad            numeric(18,4) not null check (cantidad > 0),
  fecha               date not null default current_date,
  proveedor           text,
  forma_pago          text not null check (forma_pago in ('EFECTIVO','BANCO','TARJETA','CREDITO_PROVEEDOR')),
  cuenta_financiera_id uuid references cuentas_financieras(id),
  moneda_id           uuid not null references monedas(id),
  tasa_cambio_id      uuid references tasas_cambio(id),
  created_at          timestamptz not null default now(),
  constraint chk_compra_medio_pago check (
    (forma_pago = 'CREDITO_PROVEEDOR' and cuenta_financiera_id is null) or
    (forma_pago <> 'CREDITO_PROVEEDOR' and cuenta_financiera_id is not null)
  )
);
create index idx_compras_negocio_fecha on compras(negocio_id, fecha desc);
alter table compras enable row level security;
create policy compras_isolation on compras
  using (cuenta_id = auth.uid() and (negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));
```
[Source: architecture/database-schema.md]

### Ledger vs. saldo denormalizado

`cuentas_financieras.saldo_actual` se actualiza en la misma transacción que cada `INSERT` a `movimientos_cuenta`/`movimientos_tarjeta` vía la función de aplicación `aplicarMovimiento` en `packages/database` (no vía trigger de Postgres, para que sea testeable con Vitest). El ledger es la fuente de verdad auditable; el saldo denormalizado es una proyección para lectura rápida.
[Source: architecture/database-schema.md — Notas de diseño transversales al esquema]

### Coding Standards Relevantes

- Dinero como Decimal, nunca `number`.
- Moneda Siempre Acompañada.
- Tasa de Cambio Inmutable: si la compra es en moneda distinta a Guaraní, usar el `tasaCambioId` vigente en el momento de creación — nunca recalcular con la tasa "actual" después.
- Contexto de Negocio Obligatorio: toda la lógica de esta Server Action pasa por `withRlsContext(cuentaId, negocioId, fn)`.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]

### Completion Notes List

- **Bloqueo estructural identificado y consultado con el usuario antes de implementar:** la tabla `compras`, tal como la documentan los Dev Notes de esta story, tiene FKs a `cuentas_financieras` (Story 4.3) y `tasas_cambio` (Story 5.3) — ninguna de las dos existe. Postgres no permite crear una FK contra una tabla inexistente. Se le preguntó al usuario cómo proceder; eligió "implementar lo posible, dejar FKs pendientes". Documentado explícitamente como deuda técnica en el comentario del modelo Prisma y en la migración: cuando Story 4.3/5.3 creen esas tablas, deben agregar ahí mismo `ALTER TABLE compras ADD CONSTRAINT ... FOREIGN KEY ...` — no se inventó el diseño de esas tablas acá (Article IV, No Invention).
- **Task 1 — completa.** `registrarCompraSchema` valida formato/consistencia estructural (Zod no tiene acceso a datos, así que no puede validar "el itemId es un Producto" por sí solo). La Server Action resuelve el ítem bajo `withRlsContext` (RLS ya rechaza "de otro negocio": si el item no es visible, `findUniqueOrThrow` falla) y llama a `assertItemEsProducto` (función pura, mismo patrón que `assertNegocioActivo`/`assertCambioDeTipoPermitido`) para rechazar un Servicio.
- **Task 2 — parcial, honestamente marcada así, y es la limitación central de esta story.** El efecto sobre `items.stock_actual` (increment) y `tiene_movimientos = true` está completo y ocurre en la misma transacción que el `INSERT` de la compra. El ajuste de saldo de `CuentaFinanciera` (AC3, la mitad no cubierta) y el aumento de deuda de tarjeta (AC4) **no se implementaron**: no existe `CuentaFinanciera`, `MovimientoCuenta` ni `MovimientoTarjeta` todavía. La compra igual guarda `formaPago`/`cuentaFinancieraId`/`monedaId`/`tasaCambioId` tal como el usuario los cargó, para que Story 4.2/4.3 puedan procesar retroactivamente las compras ya registradas sin perder esa información (aunque, dado que `cuenta_financiera_id` no tiene FK todavía, ese id no está validado contra ninguna tabla real — es responsabilidad de Story 4.3 decidir si valida/migra esos valores).
- **Task 3 — completa, con una limitación de UX documentada.** `CompraForm` no tiene un selector real de "cuenta financiera" (ese catálogo es Story 4.3) — usa un input de texto libre para el id, con placeholder "pendiente Story 4.3". Es funcional pero rudimentario a propósito: no se inventó un catálogo de cuentas financieras adelantado a su story.
- **Task 4 — parcial, mismo motivo estructural que las stories anteriores.** El test de dominio de `itemId` de Servicio está cubierto (`compra.test.ts`), más 5 casos adicionales del schema (`formaPago`/`cuentaFinancieraId`/`cantidad`). El test de integración no se implementó: además del bloqueo estructural ya conocido (sin Postgres de test, sin Story 1.5), la mitad de lo que debería verificar (ajuste de saldo/deuda) directamente no existe como funcionalidad todavía.
- Story queda en `Ready for Review`, no `Done`: AC3 (mitad de saldo) y AC4 completos dependen de Epic 4; falta test de integración.
