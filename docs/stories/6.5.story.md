## Story

**As a** dueño de cuenta,
**I want** definir cuánto reservar y ver mi balance personal completo,
**so that** sepa cuánto tengo realmente disponible después de mis compromisos y mi ahorro, sin importar de cuál de mis negocios provino.

## Acceptance Criteria

1. El usuario puede definir un objetivo de reserva financiera y cuánto destinar por período, y ver el progreso acumulado hacia ese objetivo (FR31).
2. El sistema calcula el balance personal como: retiros recibidos de todos los negocios − gastos fijos − gastos varios − aporte a reserva = disponible (FR32).
3. El usuario puede ver el desglose de los retiros recibidos por negocio de origen dentro del balance personal.
4. La deuda de tarjeta de crédito personal se muestra aparte, como pasivo pendiente, sin restarse directamente del disponible calculado.
5. El usuario puede responder "cuánto puedo gastar/reservar" viendo una única pantalla, sin cálculo externo (alineado a la meta de éxito del usuario en el brief).

## Dev Notes

### Previous Story Insights

Esta story integra: Story 6.1 (retiros, con la policy relajada de `retiros_utilidad` que permite leer todos los negocios sin bypass `'*'`), Story 6.3 (gastos personales fijos/variables) y Story 6.4 (deuda de tarjeta personal, que se muestra pero no se resta). Es la story de cierre de Epic 6 y del PRD completo — "el sistema cumple la promesa completa del brief" según la introducción del epic.

### Data Model — ReservaFinanciera

```typescript
export interface ReservaFinanciera {
  id: string;
  cuentaId: string;            // único
  objetivoMonto: string;
  aportePorPeriodo: string;
  periodo: "MENSUAL";
  progresoAcumulado: string;
  ultimoPeriodoAplicado: string | null;  // 'YYYY-MM' — idempotencia del cron, ADR-001
}
```
[Source: architecture/data-models.md#ReservaFinanciera]

### Automatización del aporte — resuelto en ADR-001

Al crear esta story no había guía sobre si el aporte a la reserva era automático o manual. **ADR-001** (`.ai/adr-001-cierre-de-periodo-automatico.md`) lo resolvió como automático, simétrico a `ReglaRetiro` (Story 6.2): el mismo job de cierre de período (Vercel Cron → `GET /api/cron/cierre-periodo` → `ejecutarCierreDePeriodo`) suma `aportePorPeriodo` a `progresoAcumulado` para cada `ReservaFinanciera` con `aportePorPeriodo > 0` y `ultimoPeriodoAplicado != periodo`. No se modela una tabla de historial de aportes (solo el acumulado) porque AC 1 solo pide ver el progreso acumulado, no un desglose por período.
[Source: architecture/backend-architecture.md#Jobs Programados (Cierre de Período), architecture/core-workflows.md#Cierre de período automático (retiro por regla + aporte a reserva) — ADR-001]

### Fórmula de Balance Personal (AC 2) — sin tipo `BalancePersonal` documentado explícitamente

No specific guidance found in architecture docs para un tipo TypeScript `BalancePersonal` con esa forma exacta — debe definirse en `packages/domain` siguiendo Type Sharing (Coding Standards), a partir de los modelos ya documentados (`RetiroUtilidad`, `Gasto`, `TipoGasto`, `ReservaFinanciera`, `CuentaFinanciera` para la deuda de tarjeta). La fórmula en sí (retiros − gastos fijos − gastos varios − aporte a reserva = disponible) es la definida literalmente en el AC 2 del epic — no debe alterarse ni reinterpretarse.

```typescript
export interface RetiroUtilidad { id: string; negocioId: string; monto: string; fecha: Date; origen: "MANUAL" | "REGLA"; reglaId: string | null; }
export interface Gasto { id: string; cuentaId: string; negocioId: string | null; ambito: "LABORAL" | "PERSONAL"; tipoGastoId: string; monto: string; }
export type ClasificacionGastoPersonal = "FIJO" | "VARIABLE" | "FINANCIERO";  // FINANCIERO agregado por ADR-002
```
[Source: architecture/data-models.md#RetiroUtilidad / ReglaRetiro, architecture/data-models.md#Gasto, architecture/data-models.md#TipoGasto]

**Nota:** la fórmula del AC 2 (retiros − gastos fijos − gastos varios − aporte a reserva = disponible) es literal del epic y no incluye un término de "gastos financieros" — un interés de tarjeta personal (`clasificacion: 'FINANCIERO'`, Story 6.4, ADR-002) **no se resta del disponible** con esta fórmula tal como está escrita. No se debe inventar un cuarto término no pedido por el AC; si esto es un olvido del PRD, es una pregunta para @po, no algo que esta story deba resolver.

### RLS relevante para "todos los negocios" sin bypass `'*'`

```sql
-- Nota: Personal necesita leer retiros de TODOS los negocios de la cuenta (FR25).
create policy retiros_isolation on retiros_utilidad
  using (cuenta_id = auth.uid());
```
A diferencia del dashboard consolidado (Story 5.4), que necesita `withRlsContextConsolidado` (bypass `'*'`) para leer ventas/gastos/saldos de todos los negocios, `retiros_utilidad` ya tiene una policy relajada que permite esta lectura con `withRlsContext(cuentaId, null, fn)` normal — no se debe usar el bypass consolidado aquí, sería una violación de "Bypass Consolidado Restringido" (Coding Standards) para una tabla que no lo necesita.
[Source: architecture/database-schema.md, architecture/coding-standards.md#Critical Fullstack Rules]

### Coding Standards Relevantes

- Dinero como Decimal, nunca `number`.
- Bypass Consolidado Restringido: `withRlsContextConsolidado` solo se importa desde `actions/consolidado/*` — esta story NO debe importarlo, aunque lea datos "de todos los negocios", porque `retiros_utilidad` ya lo permite vía su propia policy.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]
