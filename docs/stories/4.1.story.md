## Story

**As a** dueño de cuenta,
**I want** registrar cada gasto del negocio activo con su tipo,
**so that** se clasifique correctamente como Operativo o Financiero en los indicadores de ese negocio.

## Acceptance Criteria

1. El usuario puede registrar un gasto dentro del negocio activo, indicando monto, tipo de gasto (del catálogo de ese negocio, configurado en Epic 1), fecha y forma de pago (efectivo/banco/tarjeta de crédito) (FR18).
2. El gasto reduce el saldo de la cuenta/medio de pago usado en ese negocio, o aumenta la deuda de tarjeta de ese negocio si se paga con tarjeta de crédito.
3. La clasificación Operativo/Financiero del tipo de gasto elegido determina en qué indicador de ese negocio impacta (Gastos Operativos o Gastos Financieros — ver Epic 5), sin que el usuario tenga que elegirlo de nuevo en cada gasto.

### Data Model — Gasto

```typescript
export type FormaPagoGasto = "EFECTIVO" | "BANCO" | "TARJETA";

export interface Gasto {
  id: string;
  cuentaId: string;
  negocioId: string | null;   // null = Personal (ver Epic 6)
  ambito: "LABORAL" | "PERSONAL";
  tipoGastoId: string;
  monto: string;
  monedaId: string;
  fecha: Date;
  formaPago: FormaPagoGasto;
  cuentaFinancieraId: string;
}
```
El mismo modelo se reutiliza en Epic 6 para gastos Personal (`negocioId: null`, `ambito: 'PERSONAL'`) — esta story cubre exclusivamente el caso Laboral.
[Source: architecture/data-models.md#Gasto]

### Database Schema — tabla `gastos`

```sql
create table gastos (
  id uuid primary key default gen_random_uuid(),
  cuenta_id uuid not null references cuentas(id) on delete cascade,
  negocio_id uuid references negocios(id) on delete cascade,
  ambito text not null check (ambito in ('LABORAL','PERSONAL')),
  tipo_gasto_id uuid not null references tipos_gasto(id),
  monto numeric(18,4) not null check (monto > 0),
  moneda_id uuid not null references monedas(id),
  fecha date not null default current_date,
  forma_pago text not null check (forma_pago in ('EFECTIVO','BANCO','TARJETA')),
  cuenta_financiera_id uuid not null references cuentas_financieras(id),
  created_at timestamptz not null default now(),
  constraint chk_gasto_ambito check (
    (ambito = 'PERSONAL' and negocio_id is null) or
    (ambito = 'LABORAL'  and negocio_id is not null)
  )
);
create index idx_gastos_negocio_fecha on gastos(negocio_id, fecha desc);
alter table gastos enable row level security;
create policy gastos_isolation on gastos
  using (cuenta_id = auth.uid() and (negocio_id is null or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));
```
El campo `tipo_gasto_id` referencia `tipos_gasto`, cuya `clasificacion` (`OPERATIVO`/`FINANCIERO` para Laboral) ya está fijada al crear el catálogo (Epic 1) — este gasto no vuelve a preguntarla.
[Source: architecture/database-schema.md]

### Completion Notes List

- **Mismo bloqueo estructural que Story 2.2/3.1/3.3/3.4, mismo criterio ya acordado con el usuario:** AC2 (efecto sobre saldo/deuda vía `MovimientoCuenta`/`MovimientoTarjeta`/`CuentaFinanciera`) no se implementó porque esas entidades son de esta misma Epic 4 (Story 4.2/4.3) y todavía no existen — orden de implementación dentro de la propia epic. El gasto guarda `formaPago`/`cuentaFinancieraId` igual, para procesamiento retroactivo cuando esas stories se completen.
- **Task 1 — completa.** `registrarGastoSchema` no incluye `clasificacion` (se hereda, nunca se pide) ni `ambito`/`negocioId` (esta story es exclusivamente Laboral). La Server Action resuelve el `TipoGasto` bajo `withRlsContext` y llama a `assertTipoGastoLaboral` — necesario porque la policy compuesta de `tipos_gasto` (Story 1.7) permite ver filas Personal (`negocio_id IS NULL`) incluso con un negocio activo seteado (Personal debe ser visible desde cualquier contexto), así que sin este chequeo explícito se podría clasificar por error un gasto Laboral con un tipo Personal.
- **Task 2 — no implementada, es la limitación central de esta story.** Documentado en el modelo Prisma y la Server Action: cuando Story 4.2 (tarjeta) y Story 4.3 (cuentas financieras) existan, deben leer `gastos.forma_pago`/`cuenta_financiera_id` para aplicar el efecto retroactivamente a los gastos ya cargados.
- **Task 3 — completa.** `obtenerClasificacionGasto` es una función trivial (retorna `tipoGasto.clasificacion` tal cual) pero documenta la intención arquitectónica explícita del AC3 y es lo que pide testear la Task 5. El listado de gastos (`GastoForm`) muestra la clasificación heredada como dato de solo lectura, nunca como campo editable.
- **Task 4 — completa.** Se agregó también `listarGastos` (no pedida explícitamente en las Tasks, pero necesaria para que la UI muestre algo — mismo criterio que `listarItems`/`listarVentas` en stories anteriores), con join a `tipos_gasto` para resolver nombre y clasificación.
- **Task 5 — parcial, mismo motivo estructural.** El test de dominio cubre `assertTipoGastoLaboral` y `obtenerClasificacionGasto` (4 casos). El test de integración de deuda de tarjeta no se implementó: la funcionalidad que testearía (Task 2) no existe todavía.
- Story queda en `Ready for Review`, no `Done`: AC2 depende de Story 4.2/4.3 (la propia Epic 4 en curso); falta test de integración.
