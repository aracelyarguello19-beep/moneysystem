## Story

**As a** dueño de cuenta,
**I want** ver cuánto debe cada uno de mis negocios en tarjeta de crédito y otras cuentas,
**so that** no pierda de vista los pasivos de cada negocio.

## Acceptance Criteria

1. El sistema mantiene el saldo/deuda de cada tarjeta de crédito del negocio activo, aumentando con cada consumo y disminuyendo con cada pago de resumen registrado (FR19).
2. Los intereses o cargos de la tarjeta se registran automáticamente como Gasto Financiero de ese negocio.
3. El usuario puede ver el total adeudado en tarjetas de crédito y otras cuentas por pagar del negocio activo, separado y claramente distinguido de las cuentas por cobrar (activo) de ese mismo negocio.
4. El usuario puede registrar un pago de resumen de tarjeta, reduciendo la deuda de ese negocio y afectando el saldo de la cuenta usada para pagarlo, dentro del mismo negocio.

## Dev Notes

### Previous Story Insights

Story 2.2 y Story 4.1 ya disparan `MovimientoTarjeta` tipo `CONSUMO` cuando `formaPago === 'TARJETA'`. Esta story es la que completa el ciclo (pago de resumen, intereses) y expone el saldo de deuda consolidado — no reimplementa el registro de consumo.

### Data Model — CuentaFinanciera y MovimientoTarjeta

```typescript
export interface CuentaFinanciera {
  id: string;
  cuentaId: string;
  negocioId: string | null;
  ambito: "LABORAL" | "PERSONAL";
  tipo: "CAJA" | "BANCO" | "TARJETA";
  nombre: string;
  monedaId: string;
  saldoActual: string;        // Tarjeta: negativo = deuda
  limiteCredito: string | null;
}

export interface MovimientoTarjeta {
  id: string;
  cuentaFinancieraId: string;  // debe ser tipo TARJETA
  tipo: "CONSUMO" | "PAGO_RESUMEN" | "INTERES";
  monto: string;
  fecha: Date;
  referenciaTipo: "COMPRA" | "GASTO" | "MANUAL" | null;
  referenciaId: string | null;
}
```
[Source: architecture/data-models.md#CuentaFinanciera, architecture/data-models.md#MovimientoTarjeta / MovimientoCuenta]

### Ledger vs. saldo denormalizado (mecanismo central de esta story)

`cuentas_financieras.saldo_actual` se actualiza en la misma transacción que cada `INSERT` a `movimientos_tarjeta`, vía la función de aplicación `aplicarMovimiento` (no vía trigger de Postgres — se mantiene la lógica en `packages/database` para que sea testeable con Vitest sin depender de comportamiento de trigger). El ledger es la fuente de verdad auditable; el saldo denormalizado es una proyección para lectura rápida.
[Source: architecture/database-schema.md — Notas de diseño transversales al esquema]

### Database Schema — tabla `cuentas_financieras`

```sql
create table cuentas_financieras (
  id uuid primary key default gen_random_uuid(),
  cuenta_id uuid not null references cuentas(id) on delete cascade,
  negocio_id uuid references negocios(id) on delete cascade,
  ambito text not null check (ambito in ('LABORAL','PERSONAL')),
  tipo text not null check (tipo in ('CAJA','BANCO','TARJETA')),
  nombre text not null,
  moneda_id uuid not null references monedas(id),
  saldo_actual numeric(18,4) not null default 0,
  limite_credito numeric(18,4),
  created_at timestamptz not null default now(),
  constraint chk_cta_fin_ambito check ((ambito = 'PERSONAL' and negocio_id is null) or (ambito = 'LABORAL' and negocio_id is not null))
);
alter table cuentas_financieras enable row level security;
create policy cuentas_financieras_isolation on cuentas_financieras
  using (cuenta_id = auth.uid() and (negocio_id is null or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));
```
`movimiento_tarjeta` se omite en detalle en Database Schema por espacio pero "sigue exactamente el mismo patrón" de RLS que `movimientos_cuenta` (vía `exists` contra `cuentas_financieras`).

### Completion Notes List

- **Esta story es la que más deuda técnica acumulada cierra de todo el proyecto hasta ahora.** `cuentas_financieras` estaba documentada como pendiente en Story 2.2, 3.1, 3.4 y 4.1; el efecto de saldo/deuda (AC2-AC4 de esas stories) estaba explícitamente marcado "no implementado". Al crear la tabla y el ledger acá, se retomaron las cinco Server Actions afectadas (`registrarCompra`, `registrarVenta`, `cancelarVenta`, `registrarGasto`, `registrarPagoCxC`) para completar ese wiring — no quedó como deuda adicional. Ver Change Log de cada una de esas stories para el detalle puntual.
- **Decisión de diseño no explícita en ninguna story: dónde crear `cuentas_financieras`.** Story 4.2 y Story 4.3 documentan exactamente el mismo DDL en sus Dev Notes — ninguna de las dos dice explícitamente "yo la creo". Se decidió crear la tabla acá (4.2), porque es la primera en necesitarla end-to-end (deuda de tarjeta) según el orden numérico; Story 4.3 solo agrega Server Actions/UI de CAJA/BANCO sobre la tabla ya existente, sin migración propia.
- **Gap real encontrado en las stories: nada crea una tarjeta.** Ninguna Task de 4.1/4.2/4.3 define una Server Action para dar de alta una `CuentaFinanciera` tipo TARJETA — Story 4.3 la excluye explícitamente de `crearCuentaFinanciera`, y Story 4.2 asume que "ya existe". Sin esto, la funcionalidad de esta story sería inalcanzable (no habría ninguna tarjeta sobre la que operar). Se agregó `crearTarjeta` (`apps/web/src/actions/gastos/crear-tarjeta.ts`) como el mínimo necesario para que lo ya implementado sea usable — documentado explícitamente como un gap de especificación detectado, no como una story nueva inventada (Article IV, No Invention: se llenó un vacío obvio de dependencia, no se diseñó una funcionalidad no pedida).
- **Task 1 — completa.** `aplicarMovimientoCuenta`/`aplicarMovimientoTarjeta` (`packages/database/src/ledger.ts`) crean el movimiento y actualizan `saldoActual` en la misma llamada, usando `Prisma.Decimal`. El signo (`INGRESO`/`EGRESO`, `CONSUMO`/`PAGO_RESUMEN`/`INTERES`) se extrajo a `signoMovimientoCuenta`/`signoMovimientoTarjeta` (funciones puras en `packages/domain`) para poder testearlo sin infraestructura — es lo que cubre el test de dominio de Task 5.
- **Task 2 — completa.** `registrarInteresTarjeta` valida que la tarjeta sea tipo TARJETA (`assertCuentaFinancieraEsTarjeta`) y que el tipo de gasto elegido sea Laboral + Financiero (`assertTipoGastoLaboral` + `assertTipoGastoFinanciero`, esta última nueva) antes de aplicar el movimiento y crear el gasto en la misma transacción.
- **Task 3 — completa.** `registrarPagoResumenTarjeta` valida que la tarjeta sea TARJETA y la cuenta de origen NO sea TARJETA (`assertCuentaFinancieraNoEsTarjeta`) antes de aplicar ambos movimientos.
- **Task 4 — completa, con una aclaración sobre alcance.** La vista muestra el total adeudado en tarjetas. No se agregó una noción de "otras cuentas por pagar" más allá de tarjeta: revisando el data model completo del proyecto, no existe una entidad `CuentaPorPagar` (a diferencia de `CuentaPorCobrar`, que sí está modelada) — la deuda con proveedores (`CREDITO_PROVEEDOR` en `Compra`) se documenta como forma de pago pero no tiene ledger ni vista propia en ninguna story. No se inventó esa funcionalidad.
- **Task 5 — parcial, mismo motivo estructural que las stories anteriores.** El test de dominio del signo de cada tipo de movimiento está completo. El test de integración de "pago de resumen reduce deuda y saldo" no se implementó (Story 1.5 no existe, sin infraestructura de Postgres de test) — a diferencia de otras veces, acá la funcionalidad que testearía sí existe completa, solo falta la infraestructura para probarla contra Postgres real.
- Story queda en `Ready for Review`, no `Done`: falta el test de integración (bloqueo estructural, no funcional).
