## Story

**As a** dueño de cuenta,
**I want** registrar cuánto me costó prestar un servicio que vendí en el negocio activo,
**so that** el sistema pueda calcular correctamente el CSV de ese negocio.

## Acceptance Criteria

1. Al vender un ítem tipo Servicio dentro del negocio activo, el usuario puede registrar el costo asociado a prestarlo (mano de obra, insumos, terceros) (FR15).
2. El costo de servicio registrado alimenta el cálculo de CSV en el dashboard de indicadores de ese negocio (ver Epic 5), separado del CMV de productos.
3. Si no se registra costo de servicio para una venta de servicio, el sistema lo trata como costo cero y lo señala visualmente como dato incompleto.

## Dev Notes

### Previous Story Insights

Story 3.1 crea `Venta`/`VentaItem`, incluyendo el campo `costoServicio` en el modelo de datos. Esta story completa el comportamiento de ese campo (persistencia opcional + tratamiento de default + señalización), no introduce una nueva entidad.

### Data Model — VentaItem (campo relevante)

```typescript
export interface VentaItem {
  id: string;
  ventaId: string;
  itemId: string;
  cantidad: string | null;
  precioUnitario: string;
  costoServicio: string | null;  // solo Servicio (FR15) — null tratado como 0 y señalado (AC Story 3.2)
  cantidadDevuelta: string;
}
```
La propia arquitectura ya documenta explícitamente esta regla de negocio (null → 0 y señalado) como parte del modelo de datos.
[Source: architecture/data-models.md#Venta / VentaItem]

### Database Schema — columna `costo_servicio`

```sql
create table venta_items (
  ...
  costo_servicio numeric(18,4),
  ...
);
```
`costo_servicio` es nullable a nivel de base de datos — coherente con "costo cero si no se registra", la ausencia de valor no es un error de datos.
[Source: architecture/database-schema.md]
