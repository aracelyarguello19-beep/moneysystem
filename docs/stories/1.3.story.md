## Story

**As a** dueño de cuenta,
**I want** que nadie más pueda ver ni tocar mis datos financieros,
**so that** mi información de negocio y personal permanezca privada.

## Acceptance Criteria

1. Toda consulta a datos financieros (transacciones, saldos, catálogos) queda filtrada obligatoriamente por la cuenta autenticada, a nivel de acceso a datos (no solo de interfaz) (FR2, NFR1).
2. Una prueba de integración verifica que, autenticado como la Cuenta A, ninguna operación de lectura o escritura puede afectar datos de la Cuenta B.
3. Un intento de acceder a un recurso de otra cuenta por identificador directo (ej. manipulando una URL) es rechazado, no solo ocultado en la interfaz.

## Dev Notes

### Previous Story Insights

Story 1.2 crea la tabla `cuentas` y el flujo de autenticación cuyo `auth.uid()` esta story usa como base de todo el aislamiento.

### Por qué esta prueba es contra Postgres real, no mockeada

El propio mecanismo que se está verificando (RLS) vive en Postgres, no en el código de la aplicación — un mock de Prisma pasaría trivialmente aunque las políticas RLS estuvieran mal escritas o ausentes, dando una falsa sensación de seguridad exactamente en el área que el PRD marca como crítica. `packages/database/tests` usa el servicio Postgres del job de CI con las migraciones y policies reales aplicadas.
[Source: architecture/testing-strategy.md]

### Data Access Layer — `withRlsContext`

```typescript
// packages/database/src/rls-context.ts
export async function withRlsContext<T>(
  cuentaId: string,
  negocioId: string | null,
  fn: (tx: Prisma.TransactionClient) => Promise<T>
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    await tx.$executeRawUnsafe(
      `select set_config('request.jwt.claims', $1, true)`,
      JSON.stringify({ sub: cuentaId, role: "authenticated" })
    );
    if (negocioId) {
      await tx.$executeRawUnsafe(
        `select set_config('app.active_negocio_id', $1, true)`,
        negocioId
      );
    }
    return fn(tx);
  });
}
```
Esta es la pieza más crítica de todo el backend: convierte el requisito de negocio (NFR1/NFR2) en un mecanismo que el código no puede accidentalmente saltarse. Ninguna Server Action llama a Prisma directamente — siempre pasa por `withRlsContext` (ver Coding Standards).
[Source: architecture/backend-architecture.md#Database Architecture]

### Por qué `app_user` con `NOBYPASSRLS` es obligatorio

El rol `postgres` (superuser) y `service_role` de Supabase ignoran RLS por diseño — son para tareas administrativas. Si `DATABASE_URL` de Prisma apuntara a cualquiera de esos roles, todas las políticas de este documento serían decorativas. `DATABASE_URL` (runtime de la app) usa `app_user`; una `DIRECT_URL` separada, con el rol de owner del schema, se usa solo para `prisma migrate deploy` en CI/CD.
[Source: architecture/backend-architecture.md#Database Architecture]

### Database Schema — patrón de RLS por cuenta (ejemplos representativos)

```sql
create table cuentas ( id uuid primary key references auth.users(id) on delete cascade, ... );
alter table cuentas enable row level security;
create policy cuentas_isolation on cuentas using (id = auth.uid());

create table negocios ( ..., cuenta_id uuid not null references cuentas(id) on delete cascade, ... );
alter table negocios enable row level security;
create policy negocios_isolation on negocios using (cuenta_id = auth.uid());
```
El mismo patrón (`cuenta_id = auth.uid()`, o `exists(...)` contra la tabla padre cuando no hay `cuenta_id` directo) se replica en todas las tablas transaccionales y de catálogo listadas en Database Schema.
[Source: architecture/database-schema.md]

### Coding Standards Relevantes

- **Contexto de Negocio Obligatorio:** ninguna Server Action del módulo Laboral llama a Prisma directamente — siempre pasa por `withRlsContext(cuentaId, negocioId, fn)`. Una función que reciba un `negocioId` y no lo use dentro de `withRlsContext` es un bug, no una variación aceptable.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]
