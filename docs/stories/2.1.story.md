## Story

**As a** dueño de cuenta,
**I want** dar de alta, en el negocio activo, cada cosa que vendo como producto o como servicio,
**so that** el sistema sepa después si le corresponde CMV o CSV en ese negocio.

## Acceptance Criteria

1. El usuario puede crear un ítem vendible dentro del negocio activo, eligiendo tipo Producto o Servicio (FR11).
2. Un ítem tipo Producto tiene campos de costo de compra y stock; un ítem tipo Servicio no genera stock.
3. El tipo del ítem no puede cambiarse después de tener movimientos asociados (compras o ventas), para no corromper el histórico de CMV/CSV de ese negocio.
4. El usuario puede editar el nombre, precio de venta y otros datos no estructurales del ítem en cualquier momento.
5. El catálogo de ítems del negocio activo es independiente del catálogo de cualquier otro negocio.

### Data Model — Item

```typescript
export interface Item {
  id: string;
  negocioId: string;
  tipo: "PRODUCTO" | "SERVICIO";
  nombre: string;
  precioVenta: string;       // Decimal serializado — nunca `number`
  monedaId: string;
  costoCompra: string | null;
  stockActual: string;       // "0" para Servicio, siempre
  tieneMovimientos: boolean;
}
```
`tieneMovimientos` bloquea el cambio de `tipo` una vez que hay compras/ventas asociadas (AC 3 de esta misma story).
[Source: architecture/data-models.md#Item]

### Database Schema — tabla `items`

```sql
create table items (
  id                uuid primary key default gen_random_uuid(),
  negocio_id        uuid not null references negocios(id) on delete cascade,
  cuenta_id         uuid not null references cuentas(id) on delete cascade,
  tipo              text not null check (tipo in ('PRODUCTO','SERVICIO')),
  nombre            text not null,
  precio_venta      numeric(18,4) not null check (precio_venta >= 0),
  moneda_id         uuid not null references monedas(id),
  costo_compra      numeric(18,4) check (costo_compra >= 0),
  stock_actual      numeric(18,4) not null default 0,
  tiene_movimientos boolean not null default false,
  created_at        timestamptz not null default now(),
  constraint chk_item_servicio_sin_stock check (tipo = 'PRODUCTO' or stock_actual = 0)
);
create index idx_items_negocio on items(negocio_id);
alter table items enable row level security;
create policy items_isolation on items
  using (
    cuenta_id = auth.uid()
    and (negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
         or current_setting('app.active_negocio_id', true) = '*')
  );
```
El constraint `chk_item_servicio_sin_stock` refuerza a nivel de base de datos que un Servicio nunca tenga stock — doble barrera junto al schema Zod.
[Source: architecture/database-schema.md]

### Coding Standards Relevantes

- **Dinero como Decimal, nunca `number`:** todo monto monetario es `string` (Decimal serializado) en `packages/domain` y `Prisma.Decimal` en la capa de datos. `precioVenta` y `costoCompra` deben seguir esta regla desde esta story en adelante.
- **Moneda Siempre Acompañada:** `Item` nunca expone `precioVenta`/`costoCompra` sin su `monedaId` junto.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]

### Completion Notes List

- **Task 1 — completa.** `crearItemSchema` es un `z.discriminatedUnion` sobre `tipo`: la rama `SERVICIO` usa `costoCompra: z.null().default(null)` y `stockActual: z.literal("0").default("0")` — fuerza el valor en el propio schema (no en la Server Action), doble barrera junto al check constraint `chk_item_servicio_sin_stock`. Primera vez que se modela dinero: `precioVenta`/`costoCompra`/`stockActual` viajan como `string` en `packages/domain` (`decimalStringSchema`, nuevo helper reutilizable para todas las stories de dinero que siguen) y como `Prisma.Decimal` en la capa de datos — Prisma acepta `string` directo para escribir campos `Decimal` y expone `.toString()` para leerlos, así que la conversión en las Server Actions es directa.
- **Task 2 — parcial, honestamente marcada así.** El campo `tieneMovimientos` existe en el modelo y la regla de bloqueo (`assertCambioDeTipoPermitido`, función pura en `packages/domain`, mismo patrón que `assertNegocioActivo` de Story 1.4) está implementada y testeada en `editarItem`. Pero **nada lo setea todavía a `true`** — eso ocurre "al confirmar la primera Compra o VentaItem", y ninguna de esas dos entidades existe aún (`registrarCompra` es Story 2.2, `VentaItem` es Story 3.1). Queda como responsabilidad explícita de esas stories: al confirmar la primera compra o línea de venta de un ítem, actualizar `tiene_movimientos = true` en la misma transacción. Documentado también como comentario en el modelo Prisma.
- **Task 3 — completa.** `ItemCatalogo` (`components/item-catalogo.tsx`) no usa react-hook-form/zodResolver como los catálogos de Moneda/TipoGasto: al ser un discriminated union sobre un campo (`tipo`) que el propio usuario cambia en tiempo real dentro del mismo formulario, un resolver estático de Zod no puede validar condicionalmente sin reinicializar el form — se optó por estado local simple (`useState` por campo) y dejar que la Server Action sea la fuente de verdad de validación (se muestra `result.error.message` si falla). Los campos de costo/stock solo se renderizan cuando `tipo === "PRODUCTO"`. Se agregó edición inline (nombre/precioVenta) por ítem, consistente con AC4, sin exponer edición de `tipo` en la UI (la Server Action la soporta, pero no hay affordance en pantalla para pedirla en esta story).
- **Task 4 — parcial, mismo motivo estructural que Story 1.6/1.7.** Ambos tests de dominio pedidos están completos. El test de integración contra Postgres real no se implementó (depende de Story 1.5, no existe; sin infraestructura de Postgres de test en este entorno).
- Story queda en `Ready for Review`, no `Done`: `tieneMovimientos` no se activa todavía en ningún flujo real (depende de Story 2.2/3.1) y falta el test de integración de aislamiento.
