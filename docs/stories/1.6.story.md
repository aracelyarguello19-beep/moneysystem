## Story

**As a** dueño de cuenta,
**I want** agregar las monedas que realmente uso, por separado en cada negocio y en Personal,
**so that** no cargue monedas que no me sirven ni mezcle los catálogos entre negocios.

## Acceptance Criteria

1. El usuario puede agregar, ver y desactivar monedas en el catálogo del negocio activo, de forma independiente del catálogo de cualquier otro negocio (FR7).
2. El usuario puede agregar, ver y desactivar monedas en el catálogo del módulo Personal, de forma independiente del catálogo de cualquier negocio (FR8).
3. Agregar una moneda en un negocio no la habilita automáticamente en otro negocio ni en Personal.
4. El Guaraní está disponible como moneda base de consolidación en cada negocio y en Personal por defecto (ver Epic 5).

## Dev Notes

### Previous Story Insights

Story 1.4 (alta de negocios) y Story 1.5 (aislamiento por negocio) son prerequisito directo: el catálogo de monedas usa el mismo `withRlsContext(cuentaId, negocioId, fn)` y la misma policy compuesta cuenta+negocio.

### Data Model — Moneda

```typescript
export interface Moneda {
  id: string;
  cuentaId: string;
  negocioId: string | null;
  ambito: "LABORAL" | "PERSONAL";
  codigo: string;
  nombre: string;
  esBase: boolean;
  activa: boolean;
}
```
El ámbito Personal reutiliza la misma tabla de catálogo que Laboral con `negocio_id = null` y `ambito = 'PERSONAL'`, en vez de duplicar modelos.
[Source: architecture/data-models.md#Moneda]

### Database Schema — tabla `monedas`

```sql
create table monedas (
  id          uuid primary key default gen_random_uuid(),
  cuenta_id   uuid not null references cuentas(id) on delete cascade,
  negocio_id  uuid references negocios(id) on delete cascade,
  ambito      text not null check (ambito in ('LABORAL','PERSONAL')),
  codigo      text not null,
  nombre      text not null,
  es_base     boolean not null default false,
  activa      boolean not null default true,
  created_at  timestamptz not null default now(),
  constraint chk_moneda_ambito check (
    (ambito = 'PERSONAL' and negocio_id is null) or
    (ambito = 'LABORAL'  and negocio_id is not null)
  )
);
create unique index uq_moneda_laboral on monedas(negocio_id, codigo) where ambito = 'LABORAL';
create unique index uq_moneda_personal on monedas(cuenta_id, codigo) where ambito = 'PERSONAL';
alter table monedas enable row level security;
create policy monedas_isolation on monedas
  using (
    cuenta_id = auth.uid()
    and (negocio_id is null
         or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
         or current_setting('app.active_negocio_id', true) = '*')
  );
```
Los `codigo` de moneda no están restringidos a ISO-4217 porque el usuario define sus propias monedas.
[Source: architecture/database-schema.md]

### Completion Notes List

- **Task 1 — completa.** `crearMoneda` valida con `crearMonedaSchema` (incluye el refine ambito↔negocioId) y opera dentro de `withRlsContext(cuentaId, negocioId, fn)`. `listarMonedas(negocioId)` filtra por `cuentaId`+`negocioId` explícitos (nunca implícitos, ver Story 1.5 Task 4) además de por RLS. `desactivarMoneda(monedaId, negocioId)` no usa el wrapper genérico (mismo criterio que `archivarNegocio` en Story 1.4): dentro de una única transacción RLS, busca la moneda (`findUniqueOrThrow`, falla con `NOT_FOUND` si RLS la filtra o no existe) y, si `esBase`, aborta con `FORBIDDEN` antes de tocar la fila.
- **Task 2 — completa.** `seedMonedaBase(tx, params)` (`packages/database/src/index.ts`) inserta el Guaraní base con `createMany({ skipDuplicates: true })`, idempotente contra los índices únicos parciales. Se llama desde `crearNegocio` (Story 1.4) en una segunda transacción RLS con el `negocioId` ya conocido — necesario porque la policy de `monedas` exige que `app.active_negocio_id` coincida con el `negocio_id` insertado, y ese id no existe hasta después de crear el negocio. Para Personal, se llama de forma perezosa dentro de `listarMonedas(null)`, en cada acceso (idempotente, así que no genera filas duplicadas ni overhead real más allá de un `INSERT ... ON CONFLICT DO NOTHING`).
- **Task 3 — completa.** `MonedaCatalogo` (`components/moneda-catalogo.tsx`) es un componente compartido por ámbito, usado tanto en `laboral/configuracion` (Client Component: necesita `negocioActivoId` del store Zustand, que es client-side/localStorage, por eso la página completa es `"use client"`) como en `personal/configuracion` (Server Component simple que renderiza el catálogo con `negocioId: null` fijo). El schema Zod del formulario (`monedaCamposSchema`) se extrajo de `crearMonedaSchema` para poder validar client-side solo `codigo`/`nombre` sin duplicar reglas — `ambito`/`negocioId` los completa el código a partir del contexto, nunca el usuario.
- **Task 4 — parcial, honestamente marcada así.** El test de dominio del schema Zod está completo (4 casos: ambos sentidos del refine, ambos casos válidos). El test de integración contra Postgres real pedido explícitamente por el AC2/Task 4 ("reutilizando el patrón de aislamiento de Story 1.5") **no se implementó**: Story 1.5 (`@data-engineer`) todavía no existe, no hay `packages/database/tests/aislamiento-negocios.test.ts` de qué partir, y este entorno no tiene un servicio Postgres de test contra el cual correrlo sin tocar la base real de producción del usuario (ejecutar contra ella para un test automatizado sería inapropiado). La policy RLS compuesta sí está escrita y aplicada en la migración, siguiendo textualmente el DDL de los Dev Notes de esta story y el patrón que Story 1.5 documenta — queda lista para que esa story agregue la suite de integración cuando exista la infraestructura de CI con Postgres real.
- Story queda en `Ready for Review`, no `Done`: falta el test de integración de aislamiento (bloqueado por Story 1.5/infraestructura de CI).
