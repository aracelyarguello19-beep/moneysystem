## Story

**As a** dueño de cuenta,
**I want** poder anular una venta total o parcialmente en el negocio activo,
**so that** pueda corregir errores de carga o aceptar una devolución sin que los indicadores de ese negocio queden mal.

## Acceptance Criteria

1. El usuario puede cancelar o devolver una venta existente del negocio activo, total o parcialmente (FR16).
2. La cancelación/devolución revierte el efecto de esa porción de la venta en Ingresos Netos de ese negocio.
3. Si la venta cancelada/devuelta incluía productos, el stock correspondiente se repone en ese negocio.
4. Si la venta cancelada/devuelta ya había sido cobrada, el saldo cobrado (caja/banco) de ese negocio se ajusta o se registra el reembolso correspondiente.
5. Si la venta había generado una cuenta por cobrar, esta se ajusta o cancela según la porción devuelta.

### Database Schema — columnas relevantes

```sql
create table ventas (
  ...
  estado text not null default 'ACTIVA' check (estado in ('ACTIVA','CANCELADA','DEVUELTA_PARCIAL')),
  ...
);
create table venta_items (
  ...
  cantidad_devuelta numeric(18,4) not null default 0
);
```
No hay tabla separada de "devoluciones" — el modelo representa la devolución como estado + acumulador sobre la venta original, no como una entidad nueva. No specific guidance found in architecture docs sobre un endpoint o tabla adicional de "reembolsos"; se modela como `MovimientoCuenta`/`MovimientoTarjeta` de tipo egreso referenciando la venta.
[Source: architecture/database-schema.md]

### Ledger — referencia para el reembolso

```typescript
export interface MovimientoCuenta {
  id: string;
  cuentaFinancieraId: string;
  tipo: "INGRESO" | "EGRESO";
  monto: string;
  fecha: Date;
  referenciaTipo: "COMPRA" | "VENTA" | "GASTO" | "PAGO_CXC" | "RETIRO" | "MANUAL" | null;
  referenciaId: string | null;
}
```
Usar `referenciaTipo: "VENTA"` y `referenciaId: ventaId` para trazar el reembolso hasta la venta original — consistente con el patrón de ledger append-only documentado.
[Source: architecture/data-models.md#MovimientoTarjeta / MovimientoCuenta]

### Completion Notes List

- **Mismo bloqueo estructural que Story 2.2/3.1, mismo criterio ya acordado con el usuario** (no se volvió a preguntar): AC4 (ajuste de saldo/reembolso vía `MovimientoCuenta`/`MovimientoTarjeta`, Epic 4) y AC5 (ajuste de `CuentaPorCobrar`, Story 3.4) no se implementaron porque esas entidades no existen. `cancelarVenta` deja `estado`/`cantidadDevuelta` correctos para que esas stories futuras completen el resto.
- **Task 1 — completa.** `cancelarVentaSchema` acepta `itemsDevueltos` opcional (ausente = cancelación total). La Server Action, si no se especifican líneas, calcula el pendiente de cada una (`cantidad original - cantidadDevuelta`, usando `Prisma.Decimal`, nunca aritmética de punto flotante) y las devuelve todas. `calcularEstadoVenta` (nueva función pura en `packages/domain`) decide `ACTIVA`/`DEVUELTA_PARCIAL`/`CANCELADA` según cuánto de cada línea quedó devuelto, comparando contra "1" para Servicio sin cantidad explícita (mismo criterio que `calcularTotalVenta`).
- **Task 2 — completa.** El stock se repone solo para líneas cuyo ítem es `PRODUCTO`, en la misma transacción que incrementa `cantidadDevuelta`.
- **Task 3/Task 4 — no implementadas, es la limitación central de esta story.** Sin `CuentaFinanciera`/`MovimientoCuenta`/`MovimientoTarjeta` (Epic 4) ni `CuentaPorCobrar` (Story 3.4), no hay nada real sobre lo que aplicar el ajuste. Se decidió no inventar esas estructuras acá (Article IV, No Invention) — quedan pendientes hasta que esas stories existan, momento en el que `cancelarVenta` deberá extenderse para leerlas y ajustarlas.
- **Task 5 — completa.** No hay cálculo de Ingresos Netos en esta story (Story 5.1); solo se garantiza que `estado`/`cantidadDevuelta` reflejen la devolución para que ese cálculo futuro los reste correctamente.
- **Task 6 — completa.** `VentasLista` ahora tiene "Cancelar venta" (llama a `cancelarVenta` sin `itemsDevueltos`) y, por línea, un input de cantidad + botón "Devolver" para una devolución parcial puntual. Se agregó también un indicador `devuelto: X/Y` por línea de Producto.
- **Task 7 — parcial.** El test de dominio explícito ("cadena completa... coordinar con Story 5.1") no se coordinó porque Story 5.1 no existe — en su lugar se testeó exhaustivamente `calcularEstadoVenta` (3 escenarios: activa, parcial, cancelada) y `assertDevolucionValida` (incluyendo el límite de cantidad pendiente y el caso Servicio-como-1-unidad) de forma independiente. Los tests de integración no se implementaron: uno por el bloqueo estructural ya conocido (sin Postgres de test), el otro porque `CuentaPorCobrar` no existe todavía (no hay nada que testear).
- Story queda en `Ready for Review`, no `Done`: AC4/AC5 dependen de Epic 4/Story 3.4; faltan tests de integración.
