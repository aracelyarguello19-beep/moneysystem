## Story

**As a** dueño de cuenta,
**I want** saber quién le debe a cada negocio y cuánto,
**so that** pueda hacer seguimiento y no perder dinero adeudado en ninguno de mis negocios.

## Acceptance Criteria

1. El usuario puede ver, para el negocio activo, una lista de cuentas por cobrar por cliente, con el monto adeudado, la fecha de origen y el estado (pendiente / pagado parcial / pagado) (FR17).
2. El usuario puede registrar un pago total o parcial de una cuenta por cobrar, actualizando su estado y el saldo de caja/banco de ese negocio.
3. El total adeudado por todos los clientes del negocio activo es visible como una única cifra agregada.
4. El detalle de cuánto debe un cliente específico, dentro del negocio correspondiente, es accesible en menos de 10 segundos desde el listado (alineado a la meta de éxito del usuario en el brief).

### Previous Story Insights

Story 3.1 genera la `CuentaPorCobrar` cuando `formaCobro === 'CREDITO_CLIENTE'`; Story 3.3 la ajusta ante cancelación/devolución. Esta story es la que expone el listado y permite registrar pagos — no crea CxC nuevas por sí misma.

### Data Model — CuentaPorCobrar / PagoCxC

```typescript
export type EstadoCxC = "PENDIENTE" | "PARCIAL" | "PAGADO";

export interface CuentaPorCobrar {
  id: string;
  negocioId: string;
  ventaId: string;
  cliente: string;
  montoOriginal: string;
  montoPagado: string;
  estado: EstadoCxC;
}

export interface PagoCxC {
  id: string;
  cuentaPorCobrarId: string;
  monto: string;
  fecha: Date;
  cuentaFinancieraId: string;  // dónde entró el cobro
}
```
[Source: architecture/data-models.md#CuentaPorCobrar / PagoCxC]

### Database Schema — tabla `cuentas_por_cobrar`

```sql
create table cuentas_por_cobrar (
  id uuid primary key default gen_random_uuid(),
  negocio_id uuid not null references negocios(id) on delete cascade,
  cuenta_id uuid not null references cuentas(id) on delete cascade,
  venta_id uuid not null references ventas(id),
  cliente text not null,
  monto_original numeric(18,4) not null check (monto_original >= 0),
  monto_pagado numeric(18,4) not null default 0,
  estado text not null default 'PENDIENTE' check (estado in ('PENDIENTE','PARCIAL','PAGADO')),
  created_at timestamptz not null default now()
);
create index idx_cxc_negocio_estado on cuentas_por_cobrar(negocio_id, estado);
alter table cuentas_por_cobrar enable row level security;
create policy cxc_isolation on cuentas_por_cobrar
  using (cuenta_id = auth.uid() and (negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));
```
El índice `idx_cxc_negocio_estado` está diseñado explícitamente para soportar el listado rápido por negocio+estado que exige el AC 4 (<10 segundos).
[Source: architecture/database-schema.md]

Nota: `pagos_cxc` no se muestra en detalle en Database Schema (se documenta como "sigue exactamente el mismo patrón que sus pares mostradas": RLS por `cuenta_id`/negocio vía `exists` contra `cuentas_por_cobrar`, mismo estilo que `venta_items`). [Source: architecture/database-schema.md]

### Completion Notes List

- **Esta story completa lo que le corresponde y además cierra deuda técnica de dos stories anteriores.** Los Dev Notes de esta story son explícitos: "Story 3.1 genera la CuentaPorCobrar... Story 3.3 la ajusta... esta story es la que expone el listado y permite registrar pagos — no crea CxC nuevas por sí misma." Como esa tabla no existía cuando se implementaron 3.1/3.3, ese wiring había quedado documentado como pendiente en ambas. Al crear la tabla acá, se retomó `registrarVenta` (Story 3.1) y `cancelarVenta` (Story 3.3) para completar esa parte — no quedó como deuda técnica adicional.
- **Task 1 — completa.** `listarCuentasPorCobrar` hace join con `venta` para resolver `fechaOrigen`. El total agregado (AC3) no se calcula en el servidor: se expuso `calcularTotalAdeudado` (función pura en `packages/domain`) para que la UI lo derive del mismo listado, evitando mantener la lógica de suma en dos lugares (Server Action y componente).
- **Task 2 — parcial, honestamente marcada así.** `registrarPagoCxC` no usa `withErrorHandling` (mismo criterio que `archivarNegocio`/`cancelarVenta`): necesita distinguir "pago excede el saldo" (`assertPagoValido`, VALIDATION) de "no existe/de otro negocio" (NOT_FOUND vía RLS). El ajuste de `CuentaFinanciera.saldoActual` vía `MovimientoCuenta` no se implementó — es Epic 4, no existe. `PagoCxC.cuentaFinancieraId` se guarda igual (sin FK, mismo criterio de deuda técnica que `Compra`/`Venta`) para que Story 4.3 lo procese retroactivamente.
- **Wiring retroactivo en `registrarVenta` (Story 3.1):** al crear una venta con `formaCobro === 'CREDITO_CLIENTE'`, ahora se crea la `CuentaPorCobrar` en la misma transacción, con `montoOriginal = calcularTotalVenta(itemsResueltos)` y `cliente` (garantizado no-null por el refine del schema de esa story).
- **Wiring retroactivo en `cancelarVenta` (Story 3.3):** al devolver una venta a crédito, se calcula el valor monetario de lo devuelto en esa llamada (`precioUnitario × cantidad` de cada línea afectada, con `Prisma.Decimal`) y se resta de `montoOriginal` de la CxC asociada (`Prisma.Decimal.max(0, ...)` para no bajar de cero), recalculando `estado` con `calcularEstadoCxC`. Se agregó `@unique` a `CuentaPorCobrar.ventaId` en el schema de Prisma (una venta genera a lo sumo una CxC) para poder usar `findUnique({ where: { ventaId } })` — no estaba en el schema original de esta story, es un ajuste necesario para el wiring.
- **Task 3 — completa, con una limitación de performance no verificada.** El AC4 pide que el detalle sea accesible en <10s; el Dev Notes sugiere React Query con `staleTime` corto, que el proyecto no usa (mismo criterio que Story 2.3: no hay React Query en el stack real). Se implementó con refetch simple tras cada mutación — funcionalmente correcto, pero no se hizo ninguna medición de performance real para confirmar el NFR.
- **Task 4 — parcial, mismo motivo estructural que las stories anteriores.** El test de dominio cubre los 3 estados de la máquina de CxC, `assertPagoValido` (incluyendo el límite de saldo) y `calcularTotalAdeudado`. Los tests de integración no se implementaron: uno porque el ajuste de saldo (Task 2) no existe todavía, el otro por el bloqueo estructural ya conocido (Story 1.5 no existe, sin Postgres de test).
- Story queda en `Ready for Review`, no `Done`: falta el ajuste de saldo vía Epic 4 y los tests de integración.
