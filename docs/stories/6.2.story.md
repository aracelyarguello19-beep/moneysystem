## Story

**As a** dueño de cuenta,
**I want** configurar una regla para que mis retiros se hagan solos, por cada negocio,
**so that** no tenga que pedirlos manualmente cada período.

## Acceptance Criteria

1. El usuario puede configurar, de forma independiente para cada negocio, una regla de retiro predeterminado como porcentaje fijo de la ganancia líquida de ese negocio o como monto fijo por período (FR26).
2. El sistema aplica la regla automáticamente al cierre de cada período configurado, generando el retiro correspondiente a ese negocio sin intervención manual.
3. El usuario puede desactivar la regla de un negocio o ajustar puntualmente el monto de un período específico, sin afectar la regla de otro negocio.
4. Si coexisten un retiro manual y la regla predeterminada del mismo negocio en el mismo período, el sistema deja claro en el historial cuál origina cada movimiento.

### Data Model — ReglaRetiro

```typescript
export type TipoRegla = "PORCENTAJE" | "MONTO_FIJO";

export interface ReglaRetiro {
  id: string;
  negocioId: string;          // único por negocio
  tipo: TipoRegla;
  valor: string;
  periodo: "MENSUAL";
  activa: boolean;
  ultimoPeriodoAplicado: string | null;  // 'YYYY-MM' — idempotencia del cron, ADR-001
}
```
`negocioId` es único por regla — un negocio tiene a lo sumo una `ReglaRetiro`, consistente con AC 3 ("sin afectar la regla de otro negocio").
[Source: architecture/data-models.md#RetiroUtilidad / ReglaRetiro]

### Database Schema

`regla_retiro` ahora se muestra explícita en Database Schema (dejó de estar "omitida por espacio" cuando ADR-001 le agregó la columna `ultimo_periodo_aplicado`, que no sigue el patrón genérico de las demás tablas). RLS por `negocio_id`/`cuenta_id`, `unique(negocio_id)`.
[Source: architecture/database-schema.md#REGLA DE RETIRO PREDETERMINADO]

### Mecanismo de disparo temporal — resuelto en ADR-001

**Vercel Cron Jobs** (`vercel.json`) dispara diariamente `GET /api/cron/cierre-periodo` (06:00 UTC); el Route Handler valida `CRON_SECRET` y solo ejecuta lógica si es el último día del mes (único período soportado: `MENSUAL`). La función de dominio `ejecutarCierreDePeriodo(periodo)` (packages/domain) reutiliza el mismo cálculo de monto que la Server Action manual, y usa `ultimoPeriodoAplicado` como clave de idempotencia (evita duplicar el retiro si el cron reintenta). Se descartó `pg_cron` de Supabase para no duplicar lógica de negocio fuera de TypeScript.
[Source: architecture/backend-architecture.md#Jobs Programados (Cierre de Período), architecture/deployment-architecture.md#Jobs Programados, architecture/core-workflows.md#Cierre de período automático (retiro por regla + aporte a reserva) — ADR-001]

### Completion Notes List

- **Deviación de ubicación (documentada, mismo criterio que `withRlsContextConsolidado` en Story 5.4):** el story sugiere `ejecutarCierreDePeriodo` dentro de `packages/domain`, pero ese paquete es deliberadamente puro en todo este proyecto (cero imports de Prisma en cualquier otro archivo de `packages/domain`). La función de orquestación (transacciones, iteración de negocios, Supabase Admin API) vive en `apps/web/src/lib/cron/cierre-periodo.ts`; la parte de cálculo puro (`calcularMontoRetiroPorRegla`, `debeAplicarRegla`, `periodoMensualDe`, `esUltimoDiaDelMes`, `rangoDelPeriodoMensual`) sí vive en `packages/domain/src/regla-retiro.ts` y es lo que cubren los 11 tests de dominio.
- **Enumeración cross-cuenta del cron:** el Prisma `prisma` singleton se conecta como `app_user` (NOBYPASSRLS) y no puede listar cuentas de otros usuarios por diseño (architecture: "nunca con postgres/service_role"). Para que el cron pueda iterar TODAS las cuentas del sistema sin violar esa regla, se agregó `apps/web/src/lib/supabase/admin.ts` — un cliente Supabase Admin (`service_role`) de uso exclusivo para `auth.admin.listUsers()` (enumeración a nivel de Auth, no de datos). Todo acceso a datos financieros sigue pasando exclusivamente por `withRlsContext`, nunca por este cliente — consistente con ADR-001 ("el job itera negocio por negocio, nunca usa el bypass '\*' de escritura"). Requiere que `SUPABASE_SERVICE_ROLE_KEY` esté configurada en el entorno de producción (no está seteada en este sandbox, así que el flujo del cron no se pudo invocar end-to-end en esta sesión — ver más abajo).
- **Selección de cuenta financiera de origen en el retiro automático:** ninguna AC especifica cómo elegir entre varias cuentas CAJA/BANCO de un negocio cuando el retiro es automático (a diferencia del manual de Story 6.1, acá no hay un usuario en el loop para elegir). Se usa la cuenta CAJA/BANCO más antigua del negocio (`orderBy: createdAt asc`), de forma determinística y documentada en el código — si el negocio no tiene ninguna, la regla no genera retiro ese período (pero si corresponde, si actualiza `ultimoPeriodoAplicado`, para no reintentar indefinidamente).
- **Ganancia líquida nula o negativa con regla PORCENTAJE:** no genera un `RetiroUtilidad` (violaría el `CHECK (monto > 0)` de la tabla) pero sí actualiza `ultimoPeriodoAplicado` — evita que el cron reintente sobre el mismo período en corridas futuras.
- No se pudo invocar el Route Handler del cron end-to-end en esta sesión: requiere `SUPABASE_SERVICE_ROLE_KEY` y `CRON_SECRET` configuradas (ninguna está en `.env.local` de este sandbox) y, por diseño de Vercel (ADR-001), los crons solo se disparan en Production. La lógica de negocio que sí es testeable sin esa infraestructura (`calcularMontoRetiroPorRegla`, `debeAplicarRegla`, `esUltimoDiaDelMes`, `rangoDelPeriodoMensual`) está cubierta por los 11 tests de dominio.
- No se implementó el test de integración de Task 5 contra Postgres real — consistente con el resto de tests de integración de esta sesión, ninguno se ejecutó contra el proyecto Supabase real.
