## Story

**As a** dueño de cuenta,
**I want** ver cuánto debo en mi tarjeta de crédito personal,
**so that** no pierda de vista esa deuda al planificar mis gastos.

## Acceptance Criteria

1. El sistema mantiene el saldo/deuda de la(s) tarjeta(s) de crédito personal(es), con la misma lógica de consumo/pago de resumen que la tarjeta de un negocio (FR30).
2. Los intereses/cargos de la tarjeta personal se registran como gasto financiero personal.
3. El usuario puede ver la deuda de tarjeta personal como pasivo, separado del disponible en el balance personal.

## Dev Notes

### Previous Story Insights

Story 4.2 ya implementa la lógica completa de consumo/pago de resumen/intereses de tarjeta para el caso Laboral (`ambito: 'LABORAL'`) — el propio AC 1 de esta story pide explícitamente "la misma lógica" para Personal, por lo que esta story es principalmente de reutilización/parametrización, no de diseño nuevo.

### Data Model — CuentaFinanciera (caso Personal)

```typescript
export interface CuentaFinanciera {
  id: string;
  cuentaId: string;
  negocioId: string | null;   // null = Personal
  ambito: "LABORAL" | "PERSONAL";
  tipo: "CAJA" | "BANCO" | "TARJETA";
  nombre: string;
  monedaId: string;
  saldoActual: string;        // Tarjeta: negativo = deuda
  limiteCredito: string | null;
}
```
Modelo unificado — la misma entidad `CuentaFinanciera` representa tanto tarjetas de negocio como personales, discriminadas por `ambito`/`negocioId`.
[Source: architecture/data-models.md#CuentaFinanciera]

### Database Schema — misma tabla, `ambito = 'PERSONAL'`

```sql
create table cuentas_financieras (
  ...
  negocio_id uuid references negocios(id) on delete cascade,
  ambito text not null check (ambito in ('LABORAL','PERSONAL')),
  tipo text not null check (tipo in ('CAJA','BANCO','TARJETA')),
  ...
  constraint chk_cta_fin_ambito check ((ambito = 'PERSONAL' and negocio_id is null) or (ambito = 'LABORAL' and negocio_id is not null))
);
```
No hay tabla separada para tarjeta personal — es el mismo `cuentas_financieras` con `tipo = 'TARJETA'` y `negocio_id = null`.
[Source: architecture/database-schema.md]

### Clasificación "gasto financiero personal" — resuelto en ADR-002, confirmado por @po

Al crear esta story, el catálogo Personal (`tipos_gasto`, ver Story 1.7) solo permitía `clasificacion in ('FIJO','VARIABLE')` — AC 2 de esta story ("gasto financiero personal") era irrealizable con ese constraint. **ADR-002** (`.ai/adr-002-clasificacion-financiero-personal.md`) extendió el catálogo Personal para admitir `FINANCIERO`, simétrico a Laboral:
```sql
constraint chk_tipo_gasto_ambito check (
  (ambito = 'PERSONAL' and negocio_id is null and clasificacion in ('FIJO','VARIABLE','FINANCIERO')) or
  (ambito = 'LABORAL'  and negocio_id is not null and clasificacion in ('OPERATIVO','FINANCIERO'))
)
```
`ClasificacionGastoPersonal` en TypeScript pasa a ser `"FIJO" | "VARIABLE" | "FINANCIERO"`. FR10 y Story 1.7 AC2 fueron sincronizados por @po el 2026-08-31 (ver Story 1.7 Change Log v0.2) — ya no hay contradicción entre el PRD y esta AC.
[Source: architecture/data-models.md#TipoGasto, architecture/database-schema.md#TIPOS DE GASTO, .ai/adr-002-clasificacion-financiero-personal.md, docs/stories/1.7.story.md]
