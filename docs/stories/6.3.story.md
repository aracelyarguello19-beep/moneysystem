## Story

**As a** dueño de cuenta,
**I want** registrar mis gastos personales fijos y variables por separado,
**so that** entienda mi estructura de gastos recurrentes vs. ocasionales.

## Acceptance Criteria

1. El usuario puede registrar un gasto personal fijo, asociado a un tipo de gasto del catálogo Personal clasificado como Fijo, y forma de pago (FR28).
2. El usuario puede registrar un gasto personal variable/vario, asociado a un tipo de gasto del catálogo Personal clasificado como Variable, y forma de pago (FR29).
3. Ambos tipos de gasto se reflejan por separado en el balance personal (ver Story 6.5).

### Previous Story Insights

Reutiliza directamente el modelo `Gasto` y el patrón de Server Action de Story 4.1 (Epic 4), cambiando `ambito`/`negocioId` a Personal — el ámbito Personal reutiliza las mismas tablas de catálogo/transacción que Laboral con `negocio_id = null` y `ambito = 'PERSONAL'`, en vez de duplicar modelos (principio explícito de Data Models). ### Data Model — Gasto (mismo modelo que Story 4.1, caso Personal)

### Data Model — TipoGasto (catálogo Personal)

[Source: architecture/data-models.md#TipoGasto]

### Database Schema — reutiliza la tabla `gastos` con `ambito = 'PERSONAL'`

```sql
create table gastos (
  ...
  ambito text not null check (ambito in ('LABORAL','PERSONAL')),
  ...
  constraint chk_gasto_ambito check (
    (ambito = 'PERSONAL' and negocio_id is null) or
    (ambito = 'LABORAL'  and negocio_id is not null)
  )
);
alter table gastos enable row level security;
create policy gastos_isolation on gastos
  using (cuenta_id = auth.uid() and (negocio_id is null or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));
```
Cuando `negocio_id is null`, la policy solo exige `cuenta_id = auth.uid()` — coherente con que Personal no tiene "negocio activo".
[Source: architecture/database-schema.md]

### Completion Notes List

- No se duplicó el schema Zod: `registrarGastoPersonal` reutiliza `registrarGastoSchema` (mismos campos exactos que Story 4.1) — el discriminador real entre Laboral/Personal no es el shape del input sino el guard `assertTipoGastoPersonal`/`assertTipoGastoLaboral`, que sí necesita resolver el `TipoGasto` contra la base (Zod no puede validar el `ambito` de una fila a partir de solo su UUID).
- Se generalizaron a `negocioId: string | null` cuatro Server Actions/componentes ya existentes para que Personal pudiera usarlos sin duplicar código: `crearCuentaFinanciera` (setea `ambito` según si `negocioId` es null), `obtenerSaldos`, `listarTarjetas`, `listarGastos`, y el prop `negocioId` de `CuentaFinancieraSelect`. Todos los call sites Laborales existentes siguen pasando un `string`, compatible sin cambios.
- Se agregó `CuentaFinancieraPersonal` (versión mínima de `SaldosPanel`, sin gestión de tasas de cambio — fuera de alcance de esta story) porque Personal parte sin ninguna `CuentaFinanciera` creada: sin este mini-formulario, `GastoPersonalForm` quedaría con el selector de cuenta financiera permanentemente vacío y el feature sería inusable de punta a punta. Se documenta como el mismo criterio de "llenar un gap obvio de dependencia" ya aplicado en Story 4.2 (`crearTarjeta`).
- La UI separa gastos Fijos y Variables en dos columnas (Task 4, AC3) y agrega una tercera sección solo-lectura para Financiero (visible únicamente si ya hay registros) — anticipando el interés de tarjeta personal de Story 6.4, sin construir todavía ese flujo.
- `assertCuentaFinancieraEsTarjeta`/`aplicarMovimientoTarjeta` para `formaPago === 'TARJETA'` ya están wireados en `registrarGastoPersonal` (Task 2), pero no hay forma de crear una tarjeta personal todavía — eso es exactamente el alcance de Story 6.4 (deuda técnica esperada, no un gap de esta story).
