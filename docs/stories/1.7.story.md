## Story

**As a** dueño de cuenta,
**I want** crear mis propios tipos de gasto y clasificarlos correctamente en cada negocio,
**so that** los indicadores financieros de cada uno se calculen bien desde el primer gasto que registre.

## Acceptance Criteria

1. El usuario puede crear tipos de gasto en el catálogo del negocio activo, clasificando cada uno obligatoriamente como Operativo o Financiero al momento de crearlo (FR9, NFR7).
2. El usuario puede crear tipos de gasto en el catálogo Personal, clasificando cada uno obligatoriamente como Fijo, Variable o Financiero al momento de crearlo (FR10, NFR7). Financiero es para intereses/cargos de tarjeta de crédito personal (ver Story 6.4).
3. No es posible guardar un tipo de gasto sin su clasificación.
4. El catálogo de tipos de gasto de cada negocio es independiente del de los demás negocios y del de Personal (un tipo creado en uno no aparece en otro).

```typescript
  clasificacion: ClasificacionGastoLaboral | ClasificacionGastoPersonal;
}
```
[Source: architecture/data-models.md#TipoGasto]

### Database Schema — tabla `tipos_gasto`

```sql
create table tipos_gasto (
  id             uuid primary key default gen_random_uuid(),
  cuenta_id      uuid not null references cuentas(id) on delete cascade,
  negocio_id     uuid references negocios(id) on delete cascade,
  ambito         text not null check (ambito in ('LABORAL','PERSONAL')),
  nombre         text not null,
  clasificacion  text not null,
  created_at     timestamptz not null default now(),
  constraint chk_tipo_gasto_ambito check (
    (ambito = 'PERSONAL' and negocio_id is null and clasificacion in ('FIJO','VARIABLE','FINANCIERO')) or
    (ambito = 'LABORAL'  and negocio_id is not null and clasificacion in ('OPERATIVO','FINANCIERO'))
  )
);
alter table tipos_gasto enable row level security;
create policy tipos_gasto_isolation on tipos_gasto
  using (
    cuenta_id = auth.uid()
    and (negocio_id is null
         or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
         or current_setting('app.active_negocio_id', true) = '*')
  );
```
El `check constraint` `chk_tipo_gasto_ambito` refuerza a nivel de base de datos la misma regla que el schema Zod valida en la Server Action (AC 3) — doble barrera, no solo validación de UI.

### Completion Notes List

- **Task 1 — completa.** `crearTipoGastoSchema` es un `z.discriminatedUnion` sobre `ambito`: cada rama exige su propia `clasificacion` (enum distinto) y su propia regla de `negocioId` — rechaza en un solo schema tanto la clasificación ausente (AC3) como la combinación ambito/clasificación inválida (AC1/AC2), sin `refine` manual. `crearTipoGasto`/`listarTiposGasto` siguen el mismo patrón que `crearMoneda`/`listarMonedas` de Story 1.6 (mismo directorio `actions/catalogos/`, mismo uso de `withRlsContext`). Esta story no pide `desactivarTipoGasto` (no está en ningún AC ni Task) — no se implementó, para no inventar alcance.
- **Task 2 — completa.** `TipoGastoCatalogo` (`components/tipo-gasto-catalogo.tsx`) es el componente compartido por ámbito, mismo patrón que `MonedaCatalogo`. El `<select>` de clasificación solo ofrece las opciones válidas para el `ambito` recibido por prop (`OPCIONES_CLASIFICACION`), y el formulario usa `mode: "onChange"` + `isValid` para deshabilitar el submit hasta que haya una clasificación seleccionada — cumple "exige seleccionar la clasificación... antes de habilitar el submit" literalmente. Se agregó como una sección más de `laboral/configuracion` y `personal/configuracion` (Story 1.6), no como páginas nuevas.
- **Task 3 — parcial, mismo motivo documentado en Story 1.6.** El test de dominio cubre los 6 casos relevantes (sin clasificación en cada ámbito, clasificación cruzada inválida en cada ámbito, combinación válida en cada ámbito). El test de integración contra Postgres real no se implementó: depende de Story 1.5 (`@data-engineer`, no existe todavía) y de infraestructura de CI con Postgres real que este entorno no tiene.
- Story queda en `Ready for Review`, no `Done`: falta el test de integración de aislamiento (mismo bloqueo estructural que Story 1.6).
