## Story

**As a** dueño de cuenta,
**I want** ver el total consolidado en Guaraníes del negocio activo además del detalle por cada moneda,
**so that** tenga una única cifra de referencia aunque ese negocio opere en varias monedas.

## Acceptance Criteria

1. El usuario puede cargar y actualizar manualmente la tasa de cambio de cada moneda no base habilitada en el negocio activo (FR36).
2. El sistema muestra, para el negocio activo y junto al detalle por moneda, un total consolidado en Guaraníes que convierte cada saldo en otra moneda usando la última tasa de cambio cargada por el usuario (FR34, FR36).
3. Cada transacción en moneda distinta al Guaraní queda asociada a la tasa de cambio vigente en ese momento, de forma persistente (FR35).
4. Un reporte de un período pasado de ese negocio no cambia si el usuario carga una tasa de cambio nueva después (verificado con una prueba automatizada).
5. El usuario puede ver, para cada moneda no base de ese negocio, qué tasa se usó y en qué fecha se registró.

## Dev Notes

### Previous Story Insights

Depende de Story 4.3 (saldos por moneda, base a consolidar) y del principio "Tasa de Cambio Inmutable" que Coding Standards ya exige desde antes — esta story es la primera en implementar la entidad `TasaCambio` y la función de conversión en sí.

### Data Model — TasaCambio

```typescript
export interface TasaCambio {
  id: string;
  monedaId: string;
  tasa: string;              // 1 unidad de `monedaId` = `tasa` Guaraníes
  vigenteDesde: Date;
  registradaPor: string;     // cuentaId
}
```
Snapshot inmutable de la tasa de cambio manual cargada por el usuario para una moneda no base. Cada transacción en moneda distinta a Guaraní queda asociada a la tasa vigente en ese momento — el histórico nunca se recalcula.
[Source: architecture/data-models.md#TasaCambio]

### Database Schema — tabla `tasas_cambio`

```sql
create table tasas_cambio (
  id uuid primary key default gen_random_uuid(),
  moneda_id uuid not null references monedas(id) on delete cascade,
  tasa numeric(18,6) not null check (tasa > 0),
  vigente_desde timestamptz not null default now(),
  registrada_por uuid not null references cuentas(id),
  created_at timestamptz not null default now()
);
create index idx_tasas_moneda_vigencia on tasas_cambio(moneda_id, vigente_desde desc);
alter table tasas_cambio enable row level security;
create policy tasas_cambio_isolation on tasas_cambio
  using (registrada_por = auth.uid());  -- moneda ya está aislada aguas arriba; se refuerza por dueño
```
El índice `idx_tasas_moneda_vigencia` está diseñado para resolver eficientemente "la tasa vigente a una fecha dada" (`order by vigente_desde desc limit 1 where vigente_desde <= :fecha`).
[Source: architecture/database-schema.md]

### Coding Standards — regla central de esta story

**Tasa de Cambio Inmutable:** una transacción nunca recalcula su conversión a Guaraníes leyendo la tasa "actual" — siempre usa el `tasaCambioId` que quedó grabado en el momento de creación (FR35). Un reporte histórico jamás vuelve a resolver la tasa vigente hoy.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]

### Completion Notes List

- **Corrección de un problema real en Story 2.2/3.1: `tasaCambioId` era un campo que el cliente podía enviar directamente.** Los schemas `registrarCompraSchema`/`registrarVentaSchema` aceptaban `tasaCambioId: z.string().uuid().nullable()` como input del formulario — inofensivo mientras `tasas_cambio` no existía (siempre se guardaba `null`), pero una vez que la tabla existe, dejar que el cliente elija la tasa violaría directamente el Coding Standard "Tasa de Cambio Inmutable" (AC3/AC4 de esta story). Se eliminó el campo de ambos schemas y se resuelve 100% server-side con `resolverTasaCambioVigente` — los formularios ya no envían ese campo (se limpiaron `compra-form.tsx`/`registrar-venta-form.tsx`, que mandaban `tasaCambioId: null` sin ningún efecto real).
- **Riesgo de seguridad identificado y corregido en `registrarTasaCambio`:** una foreign key de Postgres valida existencia contra toda la tabla sin pasar por RLS — así que confiar solo en la FK `moneda_id → monedas(id)` hubiera permitido, en teoría, registrar una tasa para el `monedaId` de otra cuenta (la FK no lo hubiera rechazado). Se agregó `tx.moneda.findUniqueOrThrow` dentro de `withRlsContext` antes del insert, que sí respeta RLS y falla si la moneda no es visible para el usuario. Esto obligó a agregar `negocioId` a la firma de la Server Action (no estaba en la sugerida por Task 1) porque la policy compuesta de `monedas` (Story 1.6) solo hace visible una moneda LABORAL cuando `app.active_negocio_id` coincide con su negocio.
- **Task 3 — firma de `convertirAGuaranies` distinta a la sugerida, y por qué.** La firma propuesta en Task 1 (`convertirAGuaranies(monto, monedaId, tasaCambioId)`) implicaría que la función resuelve un `monedaId`/`tasaCambioId` a un valor de tasa real — imposible para una función pura sin acceso a datos. Se implementó como `convertirAGuaranies({ monto, esMonedaBase, tasa })`: quien la llama (Server Action o componente) resuelve primero si la moneda es base y cuál es la tasa aplicable, y esta función solo hace la multiplicación. Es la misma separación guardia/cálculo que se usó en `assertItemEsProducto`, `signoMovimientoCuenta`, etc. a lo largo de esta sesión.
- **Task 2 — completa, y es la limitación de diseño más interesante de esta story.** Al resolver `tasaCambioId` dentro de la misma transacción de `registrarCompra`/`registrarVenta`, la inmutabilidad queda garantizada estructuralmente: una vez creada la fila, nada vuelve a tocar ese campo, y ningún código de lectura (indicadores, listados) tiene una ruta para "recalcular" con la tasa actual — solo puede leer el `tasaCambioId` ya grabado. El test de "reporte histórico" (`conversion-tasa-historica.test.ts`) lo documenta explícitamente aunque sea casi tautológico dado el diseño: `convertirAGuaranies` no tiene ninguna forma de "mirar" la tasa de hoy.
- **Task 4 — completa, sin pantalla dedicada nueva.** Se integró en `SaldosPanel` (Story 4.3) en vez de crear una ruta separada — el consolidado y la gestión de tasas son parte natural de la misma vista de saldos por moneda que esa story ya construyó.
- **Task 5 — completa.** Además del test explícito de tasa histórica, se cubrió `convertirAGuaranies` para moneda base (no-op), moneda no base con tasa, y el caso sin tasa cargada todavía (devuelve `"0"` en vez de fallar — decisión consciente para no romper una vista de saldos si el usuario todavía no cargó ninguna tasa).
- Story queda en `Ready for Review`. Sin salvedades funcionales — todos los AC quedaron completos.
