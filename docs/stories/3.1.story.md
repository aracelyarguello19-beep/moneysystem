## Story

**As a** dueño de cuenta,
**I want** registrar, en el negocio activo, una venta con uno o más productos y/o servicios,
**so that** quede reflejada en los ingresos de ese negocio y, si corresponde, en el cobro.

## Acceptance Criteria

1. El usuario puede registrar, dentro del negocio activo, una venta con uno o más ítems (producto y/o servicio mezclados) del catálogo de ese negocio, cada uno con su precio de venta y cantidad cuando aplica (FR14).
2. La venta admite cliente opcional, forma de cobro (efectivo/banco/tarjeta/a crédito) e impuesto sobre la venta aplicado si corresponde.
3. Si la venta incluye productos, el stock de cada producto vendido se reduce en la cantidad correspondiente, dentro de ese negocio.
4. Si la forma de cobro es "a crédito", se genera automáticamente una cuenta por cobrar del negocio activo, asociada al cliente, por el monto correspondiente (ver Story 3.4).
5. El impuesto sobre la venta registrado en la transacción alimenta el cálculo de Ingresos Netos de ese negocio (ver Epic 5).

### Data Model — Venta / VentaItem

```typescript
export type FormaCobro = "EFECTIVO" | "BANCO" | "TARJETA" | "CREDITO_CLIENTE";
export type EstadoVenta = "ACTIVA" | "CANCELADA" | "DEVUELTA_PARCIAL";

export interface Venta {
  id: string;
  negocioId: string;
  cliente: string | null;
  fecha: Date;
  formaCobro: FormaCobro;
  impuesto: string;           // monto de impuesto aplicado, alimenta Ingresos Netos
  estado: EstadoVenta;
  cuentaFinancieraId: string | null; // null si CREDITO_CLIENTE
  monedaId: string;
  tasaCambioId: string | null;
}

export interface VentaItem {
  id: string;
  ventaId: string;
  itemId: string;
  cantidad: string | null;    // null para Servicio sin cantidad explícita
  precioUnitario: string;
  costoServicio: string | null;  // solo Servicio — null tratado como 0 (ver Story 3.2)
  cantidadDevuelta: string;   // acumulador de devoluciones parciales (ver Story 3.3)
}
```

### Database Schema — tablas `ventas` y `venta_items`

```sql
create table ventas (
  id uuid primary key default gen_random_uuid(),
  negocio_id uuid not null references negocios(id) on delete cascade,
  cuenta_id uuid not null references cuentas(id) on delete cascade,
  cliente text,
  fecha date not null default current_date,
  forma_cobro text not null check (forma_cobro in ('EFECTIVO','BANCO','TARJETA','CREDITO_CLIENTE')),
  impuesto numeric(18,4) not null default 0,
  estado text not null default 'ACTIVA' check (estado in ('ACTIVA','CANCELADA','DEVUELTA_PARCIAL')),
  cuenta_financiera_id uuid references cuentas_financieras(id),
  moneda_id uuid not null references monedas(id),
  tasa_cambio_id uuid references tasas_cambio(id),
  created_at timestamptz not null default now()
);
create index idx_ventas_negocio_fecha on ventas(negocio_id, fecha desc);
alter table ventas enable row level security;
create policy ventas_isolation on ventas
  using (cuenta_id = auth.uid() and (negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*'));

create table venta_items (
  id uuid primary key default gen_random_uuid(),
  venta_id uuid not null references ventas(id) on delete cascade,
  item_id uuid not null references items(id),
  cantidad numeric(18,4),
  precio_unitario numeric(18,4) not null check (precio_unitario >= 0),
  costo_servicio numeric(18,4),
  cantidad_devuelta numeric(18,4) not null default 0
);
alter table venta_items enable row level security;
create policy venta_items_isolation on venta_items
  using (exists (select 1 from ventas v where v.id = venta_items.venta_id and v.cuenta_id = auth.uid()
    and (v.negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid or current_setting('app.active_negocio_id', true) = '*')));
```

  revalidatePath(`/laboral/dashboard`);

}

### Completion Notes List

- **Mismo bloqueo estructural que Story 2.2, mismo criterio ya acordado con el usuario** (no se volvió a preguntar por ser la misma categoría de decisión): `ventas` tiene FKs a `cuentas_financieras`/`tasas_cambio` (Epic 4/5, no existen) — se crearon como columnas UUID simples sin FK, documentado en el modelo Prisma y la migración para que Story 4.3/5.3 agreguen las FKs cuando corresponda.
- **Task 1 — completa.** `registrarVentaSchema` valida estructura (incluye el refine de `cliente` requerido y `cuentaFinancieraId` prohibido/obligatorio según `formaCobro`, simétrico al de `registrarCompraSchema`). La Server Action resuelve cada `VentaItem` bajo `withRlsContext` antes de escribir nada, validando con `assertCantidadValidaParaVentaItem` (nueva guardia pura en `packages/domain`, mismo patrón que `assertItemEsProducto`) que un Producto tenga cantidad válida — un Servicio puede venderse sin cantidad.
- **Task 2 — completa.** El `stock_actual` se decrementa solo para los `VentaItem` cuyo ítem es `PRODUCTO` y tiene `cantidad`, dentro de la misma transacción que crea la venta.
- **Task 3 — no implementada, es la limitación central de esta story (igual que el ajuste de saldo en Story 2.2).** No existe `CuentaPorCobrar` (Story 3.4) ni `MovimientoCuenta`/`MovimientoTarjeta` (Epic 4). La venta guarda `formaCobro`/`cliente`/`cuentaFinancieraId` tal como se cargaron, para que esas stories futuras puedan procesar retroactivamente las ventas ya registradas.
- **Task 4 — completa.** `venta.impuesto` se persiste tal cual; no hay cálculo de Ingresos Netos en esta story (es Story 5.1).
- **Task 5 — completa.** `RegistrarVentaForm` (`components/forms/registrar-venta-form.tsx`) permite agregar/quitar líneas de ítems (mezclando Producto/Servicio del catálogo), auto-completa el precio unitario al elegir el ítem, y oculta el campo cantidad para Servicio. La validación de "cliente requerido" ocurre antes de llamar a la Server Action (no hace el round-trip si va a fallar igual).
- **Task 6 — parcial, mismo motivo estructural que las stories anteriores.** El test de componente explícito de la story (`registrar-venta-form.test.tsx`) y el de dominio (`calcularTotalVenta` sobre una venta mixta) están completos. Se agregó `decimal.js` como dependencia de `packages/domain` para esta función — no había una librería de precisión decimal disponible ahí todavía (`Prisma.Decimal` vive en `packages/database`, que domain no debe depender de). El test de integración de reducción de stock no se implementó (mismo bloqueo estructural: Story 1.5 no existe, sin infraestructura de Postgres de test).
- Story queda en `Ready for Review`, no `Done`: AC4 completo y la mitad de AC2 dependen de Story 3.4/Epic 4; falta test de integración.
