## Story

**As a** dueño de cuenta,
**I want** que los datos de un negocio no se mezclen con los de otro negocio mío,
**so that** mis indicadores y saldos por negocio sean confiables.

## Acceptance Criteria

1. Toda consulta a datos transaccionales y de catálogo (compras, ventas, gastos, saldos, ítems, monedas, tipos de gasto) queda filtrada obligatoriamente por el negocio activo además de por la cuenta autenticada, a nivel de acceso a datos (FR6, NFR2).
2. Una prueba de integración verifica que, dentro de la misma cuenta, ninguna operación de lectura o escritura sobre el Negocio A puede afectar datos del Negocio B.
3. El selector de negocio activo determina exclusivamente sobre qué negocio se opera y qué datos se muestran; ninguna pantalla del módulo Laboral, salvo el dashboard consolidado (ver Epic 5), mezcla transacciones de negocios distintos.

## Dev Notes

### Previous Story Insights

Story 1.3 estableció el aislamiento por `cuenta_id` y el mecanismo `withRlsContext`. Esta story agrega la segunda dimensión de aislamiento (`negocio_id`) sobre el mismo mecanismo — no es un mecanismo nuevo, es el mismo `withRlsContext` recibiendo `negocioId`.

### Database Schema — patrón de RLS compuesto cuenta + negocio (ejemplos representativos)

```sql
create policy monedas_isolation on monedas
  using (
    cuenta_id = auth.uid()
    and (
      negocio_id is null  -- Personal: solo requiere cuenta
      or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
      or current_setting('app.active_negocio_id', true) = '*'  -- lectura consolidada, ver Epic 5
    )
  );

create policy venta_items_isolation on venta_items
  using (exists (
    select 1 from ventas v where v.id = venta_items.venta_id and v.cuenta_id = auth.uid()
    and (v.negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
         or current_setting('app.active_negocio_id', true) = '*')
  ));
```
El mismo patrón se replica en `tipos_gasto`, `items`, `cuentas_financieras`, `compras`, `ventas`, `cuentas_por_cobrar`, `gastos`, `movimientos_cuenta` (esta última vía `exists` sobre `cuentas_financieras`).

**Caso especial — `retiros_utilidad`:**
```sql
-- Nota: a diferencia de las demás tablas Laborales, Personal necesita leer
-- retiros de TODOS los negocios de la cuenta (FR25). Por eso esta policy NO
-- exige coincidencia de negocio_id para SELECT.
create policy retiros_isolation on retiros_utilidad
  using (cuenta_id = auth.uid());
```
Es la única tabla con RLS de negocio "relajada" a propósito — documentado explícitamente en el SQL para que no se lea como un descuido en una futura revisión.
[Source: architecture/database-schema.md]

### Bypass `'*'` — regla de Coding Standards

**Bypass Consolidado Restringido:** `withRlsContextConsolidado` (con `app.active_negocio_id = '*'`) solo se importa desde `actions/consolidado/*`. Ningún otro archivo del repo debe importarlo — se verifica en code review, no hay lint automático para esto (documentado como riesgo conocido). RLS no puede distinguir "intención de lectura" de "intención de escritura" dentro de la misma policy `USING`, por eso se refuerza en código, no solo en SQL.
[Source: architecture/coding-standards.md#Critical Fullstack Rules, architecture/database-schema.md]

### Data Access Layer

```typescript
export async function withRlsContext<T>(
  cuentaId: string,
  negocioId: string | null,
  fn: (tx: Prisma.TransactionClient) => Promise<T>
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    await tx.$executeRawUnsafe(`select set_config('request.jwt.claims', $1, true)`, JSON.stringify({ sub: cuentaId, role: "authenticated" }));
    if (negocioId) {
      await tx.$executeRawUnsafe(`select set_config('app.active_negocio_id', $1, true)`, negocioId);
    }
    return fn(tx);
  });
}
```
