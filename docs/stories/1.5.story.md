## Story

**As a** dueño de cuenta,
**I want** que los datos de un negocio no se mezclen con los de otro negocio mío,
**so that** mis indicadores y saldos por negocio sean confiables.

## Acceptance Criteria

1. Toda consulta a datos transaccionales y de catálogo (compras, ventas, gastos, saldos, ítems, monedas, tipos de gasto) queda filtrada obligatoriamente por el negocio activo además de por la cuenta autenticada, a nivel de acceso a datos (FR6, NFR2).
2. Una prueba de integración verifica que, dentro de la misma cuenta, ninguna operación de lectura o escritura sobre el Negocio A puede afectar datos del Negocio B.
3. El selector de negocio activo determina exclusivamente sobre qué negocio se opera y qué datos se muestran; ninguna pantalla del módulo Laboral, salvo el dashboard consolidado (ver Epic 5), mezcla transacciones de negocios distintos.

## Dev Notes

### Previous Story Insights

Story 1.3 estableció el aislamiento por `cuenta_id` y el mecanismo `withRlsContext`. Esta story agrega la segunda dimensión de aislamiento (`negocio_id`) sobre el mismo mecanismo — no es un mecanismo nuevo, es el mismo `withRlsContext` recibiendo `negocioId`.

### Database Schema — patrón de RLS compuesto cuenta + negocio (ejemplos representativos)

```sql
create policy monedas_isolation on monedas
  using (
    cuenta_id = auth.uid()
    and (
      negocio_id is null  -- Personal: solo requiere cuenta
      or negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
      or current_setting('app.active_negocio_id', true) = '*'  -- lectura consolidada, ver Epic 5
    )
  );

create policy venta_items_isolation on venta_items
  using (exists (
    select 1 from ventas v where v.id = venta_items.venta_id and v.cuenta_id = auth.uid()
    and (v.negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
         or current_setting('app.active_negocio_id', true) = '*')
  ));
```
El mismo patrón se replica en `tipos_gasto`, `items`, `cuentas_financieras`, `compras`, `ventas`, `cuentas_por_cobrar`, `gastos`, `movimientos_cuenta` (esta última vía `exists` sobre `cuentas_financieras`).

**Caso especial — `retiros_utilidad`:**
```sql
-- Nota: a diferencia de las demás tablas Laborales, Personal necesita leer
-- retiros de TODOS los negocios de la cuenta (FR25). Por eso esta policy NO
-- exige coincidencia de negocio_id para SELECT.
create policy retiros_isolation on retiros_utilidad
  using (cuenta_id = auth.uid());
```
Es la única tabla con RLS de negocio "relajada" a propósito — documentado explícitamente en el SQL para que no se lea como un descuido en una futura revisión.
[Source: architecture/database-schema.md]

### Bypass `'*'` — regla de Coding Standards

**Bypass Consolidado Restringido:** `withRlsContextConsolidado` (con `app.active_negocio_id = '*'`) solo se importa desde `actions/consolidado/*`. Ningún otro archivo del repo debe importarlo — se verifica en code review, no hay lint automático para esto (documentado como riesgo conocido). RLS no puede distinguir "intención de lectura" de "intención de escritura" dentro de la misma policy `USING`, por eso se refuerza en código, no solo en SQL.
[Source: architecture/coding-standards.md#Critical Fullstack Rules, architecture/database-schema.md]

### Data Access Layer

```typescript
export async function withRlsContext<T>(
  cuentaId: string,
  negocioId: string | null,
  fn: (tx: Prisma.TransactionClient) => Promise<T>
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    await tx.$executeRawUnsafe(`select set_config('request.jwt.claims', $1, true)`, JSON.stringify({ sub: cuentaId, role: "authenticated" }));
    if (negocioId) {
      await tx.$executeRawUnsafe(`select set_config('app.active_negocio_id', $1, true)`, negocioId);
    }
    return fn(tx);
  });
}
```

### Completion Notes List

**Task 1 y Task 2 — auditoría.** Las policies compuestas cuenta+negocio ya estaban aplicadas en la base real y versionadas en las migraciones del repo; se auditó que ambas coinciden y que cada tabla de la lista consulta efectivamente `app.active_negocio_id`. El caso especial de `retiros_utilidad` (policy relajada a propósito, `using (cuenta_id = auth.uid())` sin filtro de negocio, FR25) está documentado en el SQL de su migración, y el test lo cubre por partida doble: verifica que un retiro de otro negocio de la misma cuenta **sí** se ve, y que la policy **no** menciona `app.active_negocio_id` — así que si alguien "arregla" esa policy en el futuro creyendo que es un olvido, el test lo frena. La policy real se llama `retiros_utilidad_isolation`, no `retiros_isolation` como dice `architecture/database-schema.md`; diferencia de nombre nada más.

**Task 4 — la regla de code review pasó a ser un mecanismo.** El único archivo del repo que importa `withRlsContextConsolidado` sigue siendo `apps/web/src/actions/consolidado/obtener-dashboard-consolidado.ts` (verificado). Y el `negocioId` viaja explícito como argumento desde la UI: el negocio activo vive en un store de Zustand persistido en `localStorage` (`apps/web/src/stores/negocio-activo.store.ts`), nunca en una cookie que el servidor lea implícitamente.

Pero eso era todo lo que había: **nada impedía que un `negocioId` con valor `'*'` llegara a `withRlsContext`** desde un query param, un campo de formulario o un default mal puesto, convirtiendo silenciosamente una operación de un negocio en una sobre todos los negocios de la cuenta — exactamente el agujero que esta story existe para cerrar, y que RLS por sí sola no puede distinguir. Se agregó una guarda de runtime en `withRlsContext` que rechaza `'*'` y cualquier `negocioId` que no sea un UUID (ídem `cuentaId`). `withRlsContextConsolidado` fija el `'*'` internamente y nunca lo recibe como argumento, así que no se ve afectado. Cubierto por dos tests.

**DEFECTO ABIERTO — el bypass consolidado está roto en la base real (afecta a Epic 5, no a esta story).**

El test de esta story lo destapó. Las policies por negocio castean el setting a uuid *antes* de comparar:

```sql
negocio_id = nullif(current_setting('app.active_negocio_id', true), '')::uuid
or current_setting('app.active_negocio_id', true) = '*'
```

PostgreSQL no garantiza ni el orden de evaluación de los operandos de un `OR` ni el cortocircuito: el planner es libre de evaluar el cast primero. Con el setting en `'*'` (la lectura consolidada de Story 5.4), ese cast recibe la cadena `'*'` y la query entera aborta con `22P02 invalid input syntax for type uuid: "*"`. Verificado: **13 de 16 tablas fallan con un simple `select count(*)`**, o sea que `withRlsContextConsolidado` —y con él el dashboard consolidado de Epic 5— no puede leer nada.

Es un defecto de **disponibilidad, no de aislamiento**: ninguna fila se filtra de más, ni entre cuentas ni entre negocios. Por eso no bloquea los AC de esta story, que están verdes.

Corrección escrita y lista en `packages/database/prisma/migrations/20260901190000_rls_fix_bypass_consolidado/` (con `rollback.sql`): saca el `'*'` del operando que se castea, `nullif(nullif(current_setting(...), ''), '*')::uuid`, en vez de confiar en el orden de evaluación del `OR`. La semántica no cambia en ningún caso que hoy funcione.

**No se pudo aplicar.** Requiere el rol dueño del schema y la password de `postgres` en `DIRECT_URL` (`packages/database/.env`) es inválida (`Authentication failed against database server ... for postgres`); `app_user` no tiene `CREATE` sobre `public` ni es dueño de ninguna tabla, y el MCP de Supabase no está disponible en este contexto. Queda para @devops junto con el baselining de `_prisma_migrations` (ver Story 1.3).

Mientras el defecto siga vivo, el test lo refleja sin mentir: `aislamiento-negocios.test.ts` sondea el comportamiento real y corre **exactamente uno** de dos tests — `AC3 [DEFECTO ABIERTO]` (que verifica que el `22P02` sigue ahí y loguea un warning) mientras la migración no esté aplicada, y `AC3: el bypass consolidado ve todos los negocios...` (la aserción de verdad) apenas se aplique. Nunca hay un verde que tape el estado real.

**[AUTO-DECISION]** ¿Rechazar `'*'` en `withRlsContext` rompe algún llamador existente? → **No.** Se revisaron los 30+ llamados a `withRlsContext` en `apps/web/src/actions/`: todos pasan `cuenta.id` de `getCurrentAccount()` y un `negocioId` UUID o `null`. `npm run typecheck` y `npm test` (139 tests) quedan verdes.
