## Story

**As a** dueño de cuenta,
**I want** ver cuánto vale mi mercadería en stock, por producto y en total, en el negocio activo,
**so that** sepa cuánto capital tengo inmovilizado en inventario en ese negocio.

## Acceptance Criteria

1. El usuario puede ver el stock actual de cada producto del negocio activo, valorizado a su costo de compra (FR13).
2. El usuario puede ver el valor total de mercadería en stock del negocio activo, agregando todos sus productos.
3. El valor de inventario se actualiza inmediatamente después de cada compra y cada venta que afecte stock, dentro de ese negocio.
4. Los ítems tipo Servicio no aparecen en la vista de inventario. El inventario de un negocio no incluye productos de otro negocio.

### Previous Story Insights

Epic 3 (registro/cancelación de ventas) también afecta `stock_actual` y por lo tanto este valor, aunque su implementación detallada corresponde a esas stories.

### Data Model — Item (campos relevantes)

```typescript
export interface Item {
  id: string;
  negocioId: string;
  tipo: "PRODUCTO" | "SERVICIO";
  costoCompra: string | null;
  stockActual: string;       // "0" para Servicio, siempre
}
```
No specific guidance found in architecture docs para un tipo `ValorInventario` explícito — se deriva de `Item.stockActual * Item.costoCompra`, siguiendo la regla general de Dinero como Decimal (nunca `number`).
[Source: architecture/data-models.md#Item]

### Database Schema — filtro base

```sql
-- items: constraint chk_item_servicio_sin_stock garantiza stock_actual = 0 para SERVICIO,
-- por lo que filtrar solo por negocio_id + tipo = 'PRODUCTO' es suficiente y consistente.
select * from items where negocio_id = :negocioId and tipo = 'PRODUCTO';
```
La policy `items_isolation` ya filtra por `cuenta_id = auth.uid()` y `negocio_id` activo — no se requiere lógica adicional de aislamiento en esta query, se hereda de RLS.
[Source: architecture/database-schema.md]

### Coding Standards Relevantes

- Dinero como Decimal, nunca `number`: el cálculo `stockActual * costoCompra` debe hacerse con `Prisma.Decimal` en `packages/database` o con una librería de precisión decimal en `packages/domain`, nunca con aritmética de punto flotante de JS.
- Type Sharing: el tipo de retorno (valor por ítem + total) debe vivir en `packages/domain`.
[Source: architecture/coding-standards.md#Critical Fullstack Rules]

### Completion Notes List

- **Task 1 — completa.** `calcularValorInventario` (`packages/database/src/inventario.ts`) es una función pura (sin I/O) que recibe filas ya resueltas y usa `Prisma.Decimal` para la multiplicación stock×costo — nunca aritmética de punto flotante de JS. Filtra `tipo === "PRODUCTO"` internamente además del filtro en la query de origen (doble barrera para AC4, mismo criterio que otras stories). El tipo de retorno `ValorInventario`/`ValorInventarioItem` vive en `packages/domain` (Type Sharing), pero el cálculo vive en `packages/database` — ambas ubicaciones están explícitamente permitidas por el Coding Standard de esta story, se eligió `packages/database` para no agregar una dependencia nueva (una librería de decimales) a `packages/domain` cuando `Prisma.Decimal` ya está disponible ahí. Se agregó `@repo/domain` como dependencia formal de `packages/database` (antes no la necesitaba).
- **Task 2 — completa.** El efecto sobre `stock_actual` ya lo hacen `registrarCompra` (Story 2.2) y, en el futuro, Epic 3 — esta story no necesita ninguna lógica de recálculo propia, solo lee el valor actual en cada acceso. El Dev Notes original sugiere `revalidatePath`/`revalidateTag` o React Query con `staleTime` corto; el proyecto no tiene React Query en el stack, así que se usa `revalidatePath` (ya presente en `registrarCompra`, `crearItem`, `editarItem`). Nota honesta: como `laboral/catalogo/page.tsx` es un Client Component (necesita el negocio activo del store Zustand), `revalidatePath` no refresca automáticamente el `useEffect` de `InventarioValor` cuando otra sección de la misma página muta algo — cada componente de la página recarga sus propios datos tras sus propias mutaciones, pero no hay un mecanismo de sincronización cruzada entre `ItemCatalogo`/`CompraForm`/`InventarioValor` más allá de recargar la página. Es una limitación real, no crítica para esta story (no es una AC explícita), documentada para no dar la impresión de que quedó resuelta de forma más sofisticada de lo que está.
- **Task 3 — completa.** Se agregó como una sección más de `laboral/catalogo/page.tsx` (no una ruta dedicada) — tabla simple con producto/stock/costo/valor por fila y el total al final.
- **Task 4 — parcial, mismo motivo estructural que las stories anteriores.** El cálculo está cubierto con 3 casos (cálculo correcto, exclusión de Servicio, caso vacío) en `packages/database/src/inventario.test.ts` — primeros tests reales de ese workspace. El test de integración no se implementó (Story 1.5 no existe, sin infraestructura de Postgres de test en este entorno).
- Story queda en `Ready for Review`, no `Done`: falta el test de integración de aislamiento (mismo bloqueo que todas las stories anteriores desde Epic 1).
