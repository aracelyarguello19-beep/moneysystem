### API Specification — Health Check (único endpoint REST)

```yaml
paths:
  /health:
    get:
      summary: Estado del sistema
      security: []   # sin autenticación, por diseño (AC2 de Story 1.1)
      responses:
        "200":
          description: Sistema y base de datos operativos
          content:
            application/json:
              schema:
                type: object
                properties:
                  status: { type: string, enum: [ok] }
                  database: { type: string, enum: [connected] }
                  timestamp: { type: string, format: date-time }
        "503":
          description: Base de datos no responde
```
Este es el único endpoint REST del sistema — todo lo demás son Server Actions (ver stories siguientes). No requiere pasar por sesión porque por definición debe responder sin autenticación.
[Source: architecture/api-specification.md#Route Handler — Health Check (único endpoint REST)]

### Base de Datos — Rol de Runtime

```sql
create extension if not exists "pgcrypto";  -- gen_random_uuid()
create role app_user with login password '<gestionado por variable de entorno>' nobypassrls;
```
Crítico: el rol `postgres` (superuser) y `service_role` de Supabase ignoran RLS por diseño. Si `DATABASE_URL` apuntara a cualquiera de esos roles, todas las políticas RLS de las stories siguientes serían decorativas. `DATABASE_URL` (runtime de la app) debe usar `app_user`; una `DIRECT_URL` separada (rol owner del schema) se usa solo para `prisma migrate deploy` en CI/CD.
[Source: architecture/database-schema.md, architecture/backend-architecture.md#Database Architecture]
